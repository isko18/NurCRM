## 1. Общие сведения

### 1.1. Назначение системы
Модуль «Building» — подсистема CRM для строительной компании (застройщика).
Обеспечивает сквозной учёт деятельности по жилым комплексам (ЖК): от закупки
материалов и складского учёта до продажи квартир, расчётов с подрядчиками и
поставщиками, выплаты зарплаты и учёта долгов.

Модуль является **самодостаточным** и не зависит от других модулей платформы
(в частности, от модуля `construction`): имеет собственную кассу, собственный
механизм заявок на кассу и собственный воркфлоу согласований.

### 1.2. Цели создания
- Единый учёт всех ЖК компании и связанных с ними объектов (квартиры, склады, чертежи).
- Формализация и автоматизация процесса закупок с контролем кассы и склада.
- Управление продажами квартир, договорами (в т.ч. рассрочка) и взаиморасчётами.
- Прозрачный учёт долгов (нам должны / мы должны) и бартерных взаимозачётов.
- Учёт и расчёт заработной платы сотрудников с привязкой к ЖК.
- Полный аудит ключевых операций (журнал событий).

### 1.3. Термины и сокращения
| Термин | Расшифровка |
|--------|-------------|
| ЖК | Жилой комплекс — основной объект учёта |
| Закупка (procurement) | Заявка на приобретение материалов |
| Передача (transfer) | Перемещение позиций закупки на склад ЖК |
| AVR / Акт приёмки | Акт выполненных работ по процессу работ |
| Касса (cashbox) | Денежный фонд модуля Building |
| Заявка на кассу | Запрос на проведение денежной операции |
| Payroll | Зарплатный период и начисления |
| Owner-like | Пользователь с правами владельца/админа компании |
| Бартер | Взаимозачёт обязательств без денег |

## 2. Архитектура и технологический стек

### 2.1. Стек
- **Backend:** Python, Django, Django REST Framework.
- **БД:** реляционная (PostgreSQL), первичные ключи — UUID.
- **Фильтрация:** `django-filter` (`DjangoFilterBackend`) + `SearchFilter`.
- **Группы договоров:** иерархия на базе `django-mptt`.
- **Файлы:** загрузка через `multipart/form-data` (`FileField`).
- **Интеграция с ERP:** HTTP-вызовы через `httpx`.

### 2.2. Структура модуля
| Файл | Назначение |
|------|------------|
| `models.py` | Модели данных (~40 моделей) |
| `serializers.py` | Сериализация/валидация DRF |
| `views.py` | API-представления (generic views) |
| `services.py` | Бизнес-логика воркфлоу |
| `urls.py` | Маршрутизация (префикс `/api/building/`) |
| `admin.py` | Админ-панель |

### 2.3. Принцип мультитенантности (обязательное требование)
Все данные строго изолируются по компании пользователя:
- queryset автоматически фильтруется по `company_id` (миксин `CompanyQuerysetMixin`);
- для объектов, связанных с ЖК косвенно, — по `residential_complex__company_id`;
- `superuser` / `is_staff` имеют сквозной доступ;
- при создании/изменении объекта проверяется принадлежность связанных сущностей
  той же компании (иначе `403 PermissionDenied`).

## 3. Роли и разграничение доступа

### 3.1. Роли
| Роль | Описание |
|------|----------|
| **Owner-like** | Владелец/админ компании (`role in (owner, admin)`, владелец компании, либо `superuser`). Полный доступ ко всем разделам своей компании. |
| **Сотрудник с правами** | Доступ к разделам по набору feature-флагов. |
| **Сотрудник, назначенный на ЖК** | Видит данные только по назначенным ему ЖК. |

### 3.2. Назначения на ЖК
- Сотрудник назначается на конкретные ЖК (сущность «Сотрудник ЖК»).
- Если у сотрудника есть хотя бы одно активное назначение — он видит данные
  **только** по назначенным ЖК.
- Сотрудник без назначений (и не owner-like) — данных по ЖК не видит.
- Owner-like видит все ЖК компании.

### 3.3. Матрица прав (feature-флаги)
| Флаг | Раздел / возможность |
|------|----------------------|
| `can_view_building_procurement` | Закупки, файлы закупок, приёмка на склад |
| `can_view_building_stock` | Склад: приёмка, списания, передачи, остатки |
| `can_view_building_cash_register` | Касса, заявки на кассу, решения кассы |
| `can_view_building_clients` | Клиенты |
| `can_view_building_treaty` | Договоры, квартиры, продажи, группы договоров |
| `can_view_building_work_process` | Процесс работ, акты приёмки (AVR) |
| `can_view_building_salary` | Зарплата (payroll) |
| `can_view_building_employess` / `can_view_employees` | Сотрудники, управление назначениями на ЖК |
| `can_view_building_procurement` **или** `can_view_building_work_process` | Реестр долгов |

> Owner-like обходит проверку любого флага. Отсутствие прав → `403`.

## 4. Функциональные требования

### 4.1. Управление жилыми комплексами (ЖК)
- **FR-RC-1.** CRUD жилых комплексов в рамках компании.
- **FR-RC-2.** Управление назначениями сотрудников на ЖК (добавить/снять).
- **FR-RC-3.** CRUD чертежей ЖК (с файлами).
- **FR-RC-4.** CRUD складов ЖК (склад создаётся автоматически при первой передаче).
- **FR-RC-5.** CRUD квартир (этаж, номер, блок, комнаты, площадь, цена, статус
  `available/reserved/sold`). Требуется право `treaty`.
- **FR-RC-6.** Агрегированная статистика по этажам и по блокам (всего / свободно /
  бронь / продано).

### 4.2. Справочники
- **FR-DIR-1.** CRUD товаров (с артикулом, штрихкодом, единицей измерения).
  Уникальность штрихкода в пределах компании.
- **FR-DIR-2.** CRUD подрядчиков (тип, реквизиты, специализации, статус).
- **FR-DIR-3.** CRUD поставщиков (тип, реквизиты, банковские данные, рейтинг, статус).
- **FR-DIR-4.** История работ подрядчика и история закупок поставщика.

### 4.3. Закупки (ключевой воркфлоу)
- **FR-PROC-1.** Создание заявки на закупку (статус `draft`) с привязкой к ЖК и
  (опц.) поставщику; режим оплаты: `cash/debt/barter/mixed`.
- **FR-PROC-2.** Добавление/изменение/удаление позиций — **только** в `draft`.
  Сумма закупки пересчитывается автоматически.
- **FR-PROC-3.** Отправка закупки в кассу (`submit-to-cash`): запрещена для пустой
  закупки и не-черновика; фиксируется время и сумма.
- **FR-PROC-4.** Решение кассы: одобрить / отклонить (с обязательной причиной).
  Фиксируется решение, кто и когда принял.
- **FR-PROC-5.** Создание передачи на склад — только после одобрения кассой.
  Позиции копируются в передачу; склад ЖК создаётся при необходимости.
- **FR-PROC-6.** Прикрепление файлов к закупке; возможна авто-генерация договора
  из файла (двухшаговый сценарий).
- **FR-PROC-7.** Логирование всех переходов статусов в журнал событий.

**Диаграмма статусов закупки:**
```
draft → submitted_to_cash → cash_approved → transfer_created → transferred
                          ↘ cash_rejected            (отказ склада) ↘ partially_transferred
```

### 4.4. Склад
- **FR-WH-1.** Приёмка передачи: оприходование позиций на остатки склада,
  создание складских движений (тип `incoming`); закупка → `transferred`.
- **FR-WH-2.** При закупке в долг/бартер/смешанно с указанным поставщиком —
  автоматическое создание записи долга (PAYABLE).
- **FR-WH-3.** Отказ в приёмке (с причиной): закупка → `partially_transferred`.
- **FR-WH-4.** Складские движения: списание, передача подрядчику, передача в
  процесс работ — с корректировкой остатков.
- **FR-WH-5.** Заявки на материалы из процесса работ (статусы
  `pending/approved/rejected/partially_approved/completed`).
- **FR-WH-6.** Акты сверки по процессу работ.
- **FR-WH-7.** Просмотр текущих остатков и истории движений склада.

### 4.5. Клиенты, договоры и продажи
- **FR-TR-1.** CRUD клиентов (с файлами).
- **FR-TR-2.** CRUD договоров: тип операции (продажа/бронь/прочее), тип договора,
  тип оплаты (полная/рассрочка), режим оплаты (деньги/рассрочка/бартер/смешанный),
  статусы `draft/active/signed/cancelled`. Редактирование/удаление — только автор
  или owner-like.
- **FR-TR-3.** Рассрочка: график платежей (`planned/paid`) и регистрация платежей.
- **FR-TR-4.** Автоматическое начисление премии менеджеру при продаже
  (договор `sale`, статус active/signed) согласно настройке его вознаграждения —
  идемпотентно (без повторов по одному договору).
- **FR-TR-5.** Группировка договоров по папкам (иерархия) и перемещение договоров.
- **FR-TR-6.** Нумерация договоров (последовательность номеров).
- **FR-TR-7.** Интеграция с внешней ERP: отправка договора (статусы синхронизации
  `not_requested/requested/synced/failed/not_configured`). При отсутствии настройки
  ERP операция безопасно помечается `not_configured`.

### 4.6. Процесс работ (work entries)
- **FR-WP-1.** CRUD записей процесса работ (категория, статус работ
  `planned/in_progress/paused/completed/cancelled`, режим оплаты).
- **FR-WP-2.** Прикрепление фото и файлов.
- **FR-WP-3.** Заявки на материалы и приёмка материалов по записи.
- **FR-WP-4.** Акт приёмки работ (AVR): статусы `draft/signed`, прикрепление файлов.

### 4.7. Касса Building и заявки на кассу
- **FR-CASH-1.** CRUD касс компании/филиала (уникальность названия в рамках филиала/компании).
- **FR-CASH-2.** Движения по кассе (приход/расход; статусы `pending/approved/rejected`;
  сумма строго > 0). Массовое изменение статуса движений.
- **FR-CASH-3.** Заявки на кассу от бизнес-модулей (продажа квартиры, взнос/платёж
  по рассрочке, оплата подрядчику/закупки, аванс, прочее).
- **FR-CASH-4.** Одобрение заявки автоматически создаёт движение по кассе;
  отклонение — с причиной. Поддерживаемые статусы `pending/approved/rejected/cancelled`.
- **FR-CASH-5.** Прикрепление файлов к заявкам и движениям.

### 4.8. Зарплата (payroll)
- **FR-SAL-1.** Настройка вознаграждения сотрудника (оклад/ставка день/час/оклад+%,
  комиссия с продаж: нет/фикс/процент).
- **FR-SAL-2.** Зарплатные периоды (`draft → approved → paid`); редактирование
  только в `draft`.
- **FR-SAL-3.** Строки начислений по сотрудникам; пересчёт сумм.
- **FR-SAL-4.** Корректировки: бонус / удержание / аванс (статусы
  `pending/completed/rejected`).
- **FR-SAL-5.** Выплаты через кассу (`pending → posted/void`).
- **FR-SAL-6.** Заявки на аванс: одобрение/отклонение через кассу; авансы разрешены
  только в периодах `draft`/`approved`; проведённый аванс отменить нельзя.
- **FR-SAL-7.** Личный кабинет: просмотр сотрудником своих строк начислений.

### 4.9. Долги и бартер
- **FR-DEBT-1.** Реестр долгов: направление (нам должны / мы должны), тип операции
  (начисление/оплата/бартер/корректировка/списание), контрагент
  (клиент/поставщик/подрядчик), статусы `draft/approved/cancelled`.
- **FR-DEBT-2.** Сводка по долгам: общая и в разрезе конкретного контрагента.
- **FR-DEBT-3.** Бартер: позиции бартера для произвольного источника (upsert) и файлы.
- **FR-DEBT-4.** Бартерные зачёты с поставщиком/подрядчиком в разрезе ЖК
  (`draft → confirmed/cancelled`; удаление только в `draft`). Контрагент — строго
  поставщик XOR подрядчик.

### 4.10. Задачи и напоминания
- **FR-TASK-1.** CRUD задач (статусы `open/done/cancelled`), исполнители, файлы.
- **FR-TASK-2.** Чек-листы задач.
- **FR-TASK-3.** Доступ к задаче — автор, исполнитель или owner-like.

### 4.11. Аудит
- **FR-AUD-1.** Журнал событий воркфлоу фиксирует ключевые операции (создание/
  изменение закупок, позиций, передачи, приходы/списания, решения кассы) с
  актором, переходом статусов и полезной нагрузкой (payload).

## 6. Требования к API

- **API-1.** Все эндпоинты — REST, формат JSON; файлы — `multipart/form-data`.
- **API-2.** Базовый префикс — `/api/building/`.
- **API-3.** Все эндпоинты требуют аутентификации (`IsAuthenticated`).
- **API-4.** Списочные эндпоинты поддерживают фильтрацию и поиск (по полям,
  определённым для каждого ресурса).
- **API-5.** Идентификаторы ресурсов — UUID.
- **API-6.** Коды ответов: `200/201` — успех, `204` — удаление, `400` — ошибки
  валидации, `403` — нет прав/чужая компания, `404` — не найдено.

> Полный реестр маршрутов (~90 эндпоинтов) — см. `README.md`, раздел 3.

## 7. Нефункциональные требования

- **NFR-1. Безопасность.** Жёсткая изоляция данных по компании; проверка прав на
  каждом разделе; запрет операций над объектами чужой компании.
- **NFR-2. Целостность.** Критические операции (отправка в кассу, решение кассы,
  передача, приёмка, выплаты) выполняются в транзакциях (`@transaction.atomic`),
  складские остатки изменяются с блокировкой строки (`select_for_update`).
- **NFR-3. Согласованность сумм.** Суммы позиций, закупок и передач
  пересчитываются автоматически при изменении строк.
- **NFR-4. Аудируемость.** Ключевые переходы статусов логируются в журнал событий.
- **NFR-5. Отказоустойчивость интеграций.** Сбой/отсутствие ERP не блокирует
  работу с договором (статус фиксируется, ошибка сохраняется).
- **NFR-6. Производительность.** Использование `select_related`/`prefetch_related`,
  индексы по company/branch/status/датам.
- **NFR-7. Идемпотентность.** Повторные операции (премия с продажи) не создают дублей.

## 9. Ограничения и бизнес-правила (сводно)

1. Позиции закупки изменяются только в статусе `draft`.
2. В кассу отправляется только непустой черновик.
3. Передача создаётся только после одобрения кассой.
4. Приёмка/отказ склада возможны только для передачи в статусе `pending_receipt`.
5. Договор/запись работ редактирует/удаляет только автор или owner-like.
6. Сумма движения по кассе строго положительна.
7. Зарплатный период редактируется только в `draft`; выплаты — из `approved`.
8. Авансы разрешены в периодах `draft`/`approved`; проведённый аванс не отменяется.
9. Бартерный зачёт привязан строго к поставщику ИЛИ подрядчику (не к обоим).
10. Удаление бартерного зачёта — только в статусе `draft`.

## 10. Открытые вопросы / зоны риска

- **Валюта.** Бартерные зачёты по умолчанию в `KZT`, а долг по закупке в долг
  фиксируется в `KGS` — требуется уточнение единой валютной политики.
- **Авто-договор из файла.** Создание договора из файла закупки обёрнуто в
  «мягкий» `try/except` — ошибки молча игнорируются; стоит решить, нужна ли
  диагностика/уведомление.
- **Опечатка во флаге.** Право обозначено как `can_view_building_employess`
  (двойная `s`) — при доработках учитывать фактическое имя поля.
