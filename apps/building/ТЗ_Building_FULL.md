## 1. Общие сведения

### 1.1. Наименование системы
Подсистема «Building» — функциональный модуль CRM-платформы **nurCRM**,
предназначенный для автоматизации деятельности строительной компании
(застройщика) в разрезе жилых комплексов (ЖК).

### 1.2. Основание для разработки
Развитие платформы nurCRM: потребность застройщика в едином учёте закупок,
склада, продаж квартир, расчётов с контрагентами, зарплаты и денежного контура,
а также в интеграции денежных операций с системой бухгалтерского учёта 1С.

### 1.3. Назначение документа
Документ определяет полный набор требований к подсистеме «Building»:
функциональные и нефункциональные требования, модель данных, требования к API,
к интеграции с 1С, к видам обеспечения, состав работ и порядок приёмки.
Документ сводный: фиксирует как уже реализованную функциональность (as-is),
так и требования к интеграции с 1С (to-be).

### 1.4. Термины и сокращения
| Термин | Расшифровка |
|--------|-------------|
| ЖК | Жилой комплекс — основной объект учёта |
| Закупка (procurement) | Заявка на приобретение материалов |
| Передача (transfer) | Перемещение позиций закупки на склад ЖК |
| AVR / Акт приёмки | Акт выполненных работ по процессу работ |
| Касса (cashbox) | Денежный фонд подсистемы Building |
| Заявка на кассу | Запрос на проведение денежной операции |
| Payroll | Зарплатный период и начисления |
| Owner-like | Пользователь с правами владельца/администратора компании |
| Бартер | Взаимозачёт обязательств без денежных средств |
| Outbox | Шаблон надёжной асинхронной доставки сообщений |
| 1С | Внешняя учётная система; обмен через HTTP-сервисы (REST) |
| ПКО / РКО | Приходный / расходный кассовый ордер (документы 1С) |

## 2. Назначение и цели создания

### 2.1. Назначение
Обеспечить сквозной учёт деятельности застройщика по ЖК: закупки → склад →
процесс работ; продажи квартир → договоры → расчёты; касса, зарплата, долги;
с автоматической синхронизацией денежных операций с 1С и получением из 1С
аналитики.

### 2.2. Цели
1. Единый учёт ЖК и связанных объектов (квартиры, склады, чертежи).
2. Формализация и контроль процесса закупок (касса + склад).
3. Управление продажами, договорами, рассрочкой и взаиморасчётами.
4. Прозрачный учёт долгов и бартерных зачётов.
5. Учёт и расчёт зарплаты с привязкой к ЖК.
6. Полный аудит ключевых операций.
7. **Двусторонняя интеграция с 1С**: выгрузка всех денежных операций и
   получение из 1С подтверждений проведения, сальдо, финансовых показателей и
   справочников.

### 2.3. Критерии достижения целей
- Все данные строго изолированы по компании (мультитенантность).
- Каждая денежная операция формирует документ в 1С (с идемпотентностью).
- Аналитика 1С (сальдо, показатели) доступна в интерфейсе nurCRM.
- Недоступность 1С не блокирует работу пользователей.

## 3. Характеристика объекта автоматизации

### 3.1. Бизнес-контекст
Застройщик ведёт несколько ЖК. По каждому: закупаются материалы (с контролем
кассы и склада), выполняются работы (силами подрядчиков), продаются квартиры
(в т.ч. в рассрочку), ведутся расчёты с поставщиками/подрядчиками/клиентами,
выплачивается зарплата сотрудникам. Бухгалтерский учёт ведётся в 1С.

### 3.2. Границы автоматизации
В границах подсистемы: оперативный учёт перечисленных процессов и обмен
денежными документами/аналитикой с 1С. Вне границ: регламентированный
бухгалтерский и налоговый учёт (остаётся в 1С), банковский клиент.

## 4. Требования к системе

### 4.1. Требования к системе в целом

#### 4.1.1. Технологический стек
- Backend: Python, Django, Django REST Framework.
- БД: PostgreSQL; первичные ключи — UUID.
- Асинхронные задачи: Celery + Redis.
- Фильтрация: `django-filter` + `SearchFilter`.
- Иерархии (группы договоров): `django-mptt`.
- Файлы: `multipart/form-data` (`FileField`).
- Внешние HTTP-вызовы: `httpx` / `requests`.

#### 4.1.2. Мультитенантность (обязательно)
- Все данные изолированы по компании пользователя (`CompanyQuerysetMixin`).
- Для объектов, связанных с ЖК косвенно — фильтрация по
  `residential_complex__company_id`.
- `superuser` / `is_staff` — сквозной доступ.
- При создании/изменении проверяется принадлежность связанных сущностей той же
  компании (иначе `403`).

#### 4.1.3. Роли
| Роль | Описание |
|------|----------|
| Owner-like | Владелец/админ компании или `superuser`. Полный доступ в рамках компании. |
| Сотрудник с правами | Доступ к разделам по feature-флагам. |
| Сотрудник, назначенный на ЖК | Видит данные только по назначенным ЖК. |

Правило назначений: при наличии хотя бы одного активного назначения сотрудник
видит данные только по назначенным ЖК; без назначений (и не owner-like) — не
видит данных по ЖК.

#### 4.1.4. Матрица прав (feature-флаги)
| Флаг | Раздел |
|------|--------|
| `can_view_building_procurement` | Закупки, приёмка на склад |
| `can_view_building_stock` | Склад (приёмка, списания, передачи, остатки) |
| `can_view_building_cash_register` | Касса, заявки на кассу |
| `can_view_building_clients` | Клиенты |
| `can_view_building_treaty` | Договоры, квартиры, продажи, группы договоров |
| `can_view_building_work_process` | Процесс работ, акты приёмки |
| `can_view_building_salary` | Зарплата (payroll) |
| `can_view_building_employess` / `can_view_employees` | Сотрудники, назначения на ЖК |
| `can_view_building_procurement` **или** `can_view_building_work_process` | Реестр долгов |

> Owner-like обходит проверку любого флага. Отсутствие права → `403`.

### 4.2. Функциональные требования

#### 4.2.1. Жилые комплексы (ЖК)
- **FR-RC-1.** CRUD ЖК в рамках компании.
- **FR-RC-2.** Управление назначениями сотрудников на ЖК.
- **FR-RC-3.** CRUD чертежей ЖК (с файлами).
- **FR-RC-4.** CRUD складов ЖК (склад создаётся автоматически при первой передаче).
- **FR-RC-5.** CRUD квартир (этаж, номер, блок, комнаты, площадь, цена, статус
  `available/reserved/sold`); требуется право `treaty`.
- **FR-RC-6.** Агрегированная статистика по этажам и блокам (всего/свободно/бронь/продано).

#### 4.2.2. Справочники
- **FR-DIR-1.** CRUD товаров (артикул, штрихкод, единица; уникальность штрихкода в компании).
- **FR-DIR-2.** CRUD подрядчиков (тип, реквизиты, специализации, статус).
- **FR-DIR-3.** CRUD поставщиков (тип, реквизиты, банковские данные, рейтинг, статус).
- **FR-DIR-4.** История работ подрядчика и история закупок поставщика.

#### 4.2.3. Закупки
- **FR-PROC-1.** Создание заявки (`draft`), привязка к ЖК и (опц.) поставщику;
  режим оплаты `cash/debt/barter/mixed`.
- **FR-PROC-2.** CRUD позиций — только в `draft`; сумма пересчитывается автоматически.
- **FR-PROC-3.** Отправка в кассу: запрещена для пустой/не-черновика; фиксируется время и сумма.
- **FR-PROC-4.** Решение кассы: одобрить / отклонить (с обязательной причиной).
- **FR-PROC-5.** Создание передачи на склад — только после одобрения кассой.
- **FR-PROC-6.** Файлы к закупке; опциональная авто-генерация договора из файла.
- **FR-PROC-7.** Логирование переходов статусов.

Диаграмма статусов:
```
draft → submitted_to_cash → cash_approved → transfer_created → transferred
                          ↘ cash_rejected           (отказ склада) ↘ partially_transferred
```

#### 4.2.4. Склад
- **FR-WH-1.** Приёмка передачи: оприходование позиций, складские движения
  (`incoming`); закупка → `transferred`.
- **FR-WH-2.** Закупка в долг/бартер/смешанно с поставщиком → авто-создание записи
  долга (PAYABLE).
- **FR-WH-3.** Отказ в приёмке (с причиной) → `partially_transferred`.
- **FR-WH-4.** Движения: списание, передача подрядчику, передача в процесс работ
  (с корректировкой остатков и блокировкой строки).
- **FR-WH-5.** Заявки на материалы из процесса работ
  (`pending/approved/rejected/partially_approved/completed`).
- **FR-WH-6.** Акты сверки по процессу работ.
- **FR-WH-7.** Просмотр остатков и истории движений склада.

#### 4.2.5. Клиенты, договоры, продажи
- **FR-TR-1.** CRUD клиентов (с файлами).
- **FR-TR-2.** CRUD договоров (тип операции, тип/режим оплаты, статусы
  `draft/active/signed/cancelled`); правка/удаление — только автор или owner-like.
- **FR-TR-3.** Рассрочка: график (`planned/paid`) и регистрация платежей.
- **FR-TR-4.** Авто-начисление премии менеджеру при продаже (идемпотентно).
- **FR-TR-5.** Группировка договоров (иерархия) и перемещение.
- **FR-TR-6.** Нумерация договоров.
- **FR-TR-7.** Синхронизация договора с 1С (см. 4.2.12).

#### 4.2.6. Процесс работ
- **FR-WP-1.** CRUD записей (категория, статус `planned/in_progress/paused/completed/cancelled`, режим оплаты).
- **FR-WP-2.** Фото и файлы.
- **FR-WP-3.** Заявки на материалы и приёмка материалов по записи.
- **FR-WP-4.** Акт приёмки работ (AVR): `draft/signed`, файлы.

#### 4.2.7. Касса
- **FR-CASH-1.** CRUD касс (уникальность названия в филиале/компании).
- **FR-CASH-2.** Движения (приход/расход; `pending/approved/rejected`; сумма > 0);
  массовая смена статуса.
- **FR-CASH-3.** Заявки на кассу от бизнес-модулей (продажа, рассрочка, оплата
  подрядчику/закупки, аванс, прочее).
- **FR-CASH-4.** Одобрение заявки → авто-создание движения; отклонение — с причиной.
- **FR-CASH-5.** Файлы к заявкам и движениям.

#### 4.2.8. Зарплата (payroll)
- **FR-SAL-1.** Настройка вознаграждения (оклад/ставка/оклад+%, комиссия с продаж).
- **FR-SAL-2.** Периоды (`draft → approved → paid`); правка только в `draft`.
- **FR-SAL-3.** Строки начислений; пересчёт сумм.
- **FR-SAL-4.** Корректировки: бонус/удержание/аванс (`pending/completed/rejected`).
- **FR-SAL-5.** Выплаты через кассу (`pending → posted/void`).
- **FR-SAL-6.** Заявки на аванс: одобрение/отказ через кассу; авансы — в `draft`/`approved`;
  проведённый аванс не отменяется.
- **FR-SAL-7.** Личный кабинет: просмотр своих начислений.

#### 4.2.9. Долги и бартер
- **FR-DEBT-1.** Реестр долгов (направление, тип операции, контрагент, статусы).
- **FR-DEBT-2.** Сводки: общая и по контрагенту.
- **FR-DEBT-3.** Бартер: позиции для источника (upsert) и файлы.
- **FR-DEBT-4.** Бартерные зачёты с поставщиком/подрядчиком в разрезе ЖК
  (`draft → confirmed/cancelled`; удаление в `draft`; контрагент — поставщик XOR подрядчик).

#### 4.2.10. Задачи и напоминания
- **FR-TASK-1.** CRUD задач (`open/done/cancelled`), исполнители, файлы.
- **FR-TASK-2.** Чек-листы.
- **FR-TASK-3.** Доступ — автор, исполнитель или owner-like.

#### 4.2.11. Аудит
- **FR-AUD-1.** Журнал событий воркфлоу фиксирует ключевые операции (актор,
  переход статусов, payload).

#### 4.2.12. Интеграция с 1С (двусторонняя)
Общие параметры: транспорт — **HTTP-сервисы 1С (REST, JSON)**; режим выгрузки —
**реалтайм через Celery** (Outbox-шаблон); обмен — двусторонний.

**Outbound (nurCRM → 1С):**
- **FR-1C-O-1.** Каждая денежная операция формирует запись синхронизации
  (`OneCSyncRecord`) в той же транзакции, выгрузка — через `transaction.on_commit`.
- **FR-1C-O-2.** Выгружаются: продажи/договоры, платежи по рассрочке, движения по
  кассе, закупки и оплаты поставщикам, выплаты ЗП и авансы, записи долгов и бартер.
- **FR-1C-O-3.** Идемпотентность по ключу `{source_type}:{source_id}:{operation}`
  (наш UUID передаётся в 1С как `external_id`).
- **FR-1C-O-4.** Доставка at-least-once: Celery-ретраи с backoff; после лимита —
  статус `failed` + ручной повтор из админки.
- **FR-1C-O-5.** Сопоставление операций и документов 1С (Реализация, ПКО/РКО,
  Поступление, Ведомость, Корректировка долга) — по согласованному маппингу.

**Inbound (1С → nurCRM):**
- **FR-1C-I-1.** Подтверждение проведения: callback `POST /api/onec/callbacks/posting/`
  с HMAC-подписью; обновляет статус `OneCSyncRecord` (`posted`, номер/дата).
- **FR-1C-I-2.** Сальдо/взаиморасчёты по контрагентам (pull, Celery beat) → read-model
  + сверка с реестром долгов.
- **FR-1C-I-3.** Финансовые показатели (выручка/расходы/прибыль по ЖК/компании) →
  read-model для дашбордов.
- **FR-1C-I-4.** Справочники (номенклатура, контрагенты) → upsert в справочники
  Building (1С — источник истины, сопоставление по ИНН/коду/штрихкоду).

**Точки подключения в коде Building (где ставить `enqueue_push`):**
| Операция | Место |
|----------|-------|
| Продажа/подписание договора | `services.create_sale_commission_adjustment` / сохранение `BuildingTreaty` |
| Платёж по рассрочке | `BuildingTreatyInstallmentPaymentView` |
| Заявка на кассу → CashFlow | `CashRegisterRequestApproveView` |
| Закупка одобрена кассой | `services.approve_procurement_cash` |
| Приёмка передачи (долг) | `services.accept_transfer` |
| Выплата ЗП | `BuildingPayrollPaymentApproveView` |
| Аванс | `AdvanceRequestApproveView` |
| Долг/бартер | `BuildingDebtsLedgerListCreateView`, бартерные зачёты |

> Существующий `services.request_treaty_create_in_erp` (env `BUILDING_ERP_*`)
> обобщается новым механизмом как частный случай выгрузки договора.

### 4.4. Требования к API
- **API-1.** REST, JSON; файлы — `multipart/form-data`.
- **API-2.** Префиксы: `/api/building/` (модуль), `/api/onec/` (интеграция).
- **API-3.** Все эндпоинты требуют аутентификации (`IsAuthenticated`).
- **API-4.** Списки поддерживают фильтрацию и поиск.
- **API-5.** Идентификаторы — UUID.
- **API-6.** Коды: `200/201` — успех, `204` — удаление, `400` — валидация,
  `401` — нет/неверная аутентификация (в т.ч. подпись callback), `403` — нет
  прав/чужая компания, `404` — не найдено.

> Полный реестр маршрутов модуля (~90 эндпоинтов) — `README.md`, раздел 3.
> Эндпоинты интеграции — `INTEGRATION_1C.md`, раздел 5.

---

### 4.5. Нефункциональные требования
- **NFR-1. Безопасность.** Жёсткая изоляция по компании; проверка прав на каждом
  разделе; запрет операций над чужими объектами; секреты интеграции — только в
  зашифрованном виде, не в логах и не в ответах API.
- **NFR-2. Целостность.** Критические операции — в транзакциях
  (`@transaction.atomic`); складские остатки — с `select_for_update`; внешние
  вызовы 1С — только после commit.
- **NFR-3. Согласованность сумм.** Авто-пересчёт сумм позиций/закупок/передач.
- **NFR-4. Надёжность интеграции.** Outbox + Celery retry + dead-letter; доставка
  at-least-once; идемпотентность.
- **NFR-5. Отказоустойчивость.** Недоступность 1С не блокирует пользователя;
  синхронизация догоняет позже.
- **NFR-6. Аудируемость.** Журнал событий + журнал синхронизации с 1С.
- **NFR-7. Производительность.** `select_related`/`prefetch_related`, индексы по
  company/branch/status/датам; пагинация списков.
- **NFR-8. Масштабируемость.** Горизонтальное масштабирование воркеров Celery;
  пер-компанийная конфигурация.
- **NFR-9. Наблюдаемость.** Логирование, статусы в админке, метрики
  `failed`/`pending` синхронизации.
- **NFR-10. Идемпотентность.** Повторные операции не создают дублей (премии,
  документы 1С).

## 6. Интеграция с 1С — ключевые положения
(детально — в `INTEGRATION_1C.md`)

- **Шаблон доставки:** Outbox (`OneCSyncRecord`) + `transaction.on_commit` +
  Celery `push_to_1c` с ретраями.
- **Контракт запроса:** `POST {base_url}/documents/<type>` c телом, содержащим
  `external_id` (наш UUID), `source_type`, `operation`, `amount`, `currency`,
  контрагента, позиции, мету.
- **Inbound:** callback проведения (HMAC) + pull-задачи (сальдо, показатели,
  справочники) по расписанию Celery beat; инкрементальность через `last_pull_at`.
- **Конфигурация:** пер-компанийная модель `OneCIntegration` (URL, авторизация,
  секреты, `enabled_sources`, таймауты).

## 8. Порядок контроля и приёмки

### 8.1. Виды испытаний
- Модульные и интеграционные тесты (DRF APIClient).
- Тестирование интеграции на sandbox 1С (outbound + callback + pull).
- Нагрузочное тестирование очереди Celery (массовая выгрузка).
- Проверка безопасности: изоляция по компании, проверка прав, подпись callback.

### 8.2. Критерии приёмки
1. Денежная операция любого типа создаёт документ в 1С без дублей
   (повторная отправка идемпотентна).
2. При недоступности 1С операция в nurCRM проходит, синхронизация догоняет.
3. Подтверждение проведения из 1С корректно обновляет статус операции.
4. Сальдо и финансовые показатели из 1С отображаются в интерфейсе.
5. Все проверки прав и мультитенантности выполняются (негативные кейсы → `403`).
6. Журнал синхронизации позволяет видеть статусы и повторять `failed`-записи.

## 10. Ограничения, допущения и риски

### 10.1. Бизнес-правила (ограничения)
1. Позиции закупки изменяются только в `draft`.
2. В кассу отправляется только непустой черновик.
3. Передача создаётся только после одобрения кассой.
4. Приёмка/отказ склада — только для передачи в `pending_receipt`.
5. Договор/запись работ редактирует/удаляет только автор или owner-like.
6. Сумма движения по кассе строго положительна.
7. Зарплатный период редактируется только в `draft`; выплаты — из `approved`.
8. Авансы — в `draft`/`approved`; проведённый аванс не отменяется.
9. Бартерный зачёт — поставщик XOR подрядчик; удаление только в `draft`.

### 10.2. Допущения
- 1С публикует HTTP-сервисы и поддерживает идемпотентность по `external_id`.
- Доступен тестовый контур 1С.

### 10.3. Риски и открытые вопросы
1. **Валюта.** В Building встречаются `KGS` (долг по закупке) и `KZT` (бартер) —
   требуется единая валютная политика для документов 1С.
2. **Источник истины по долгам** — наш реестр или 1С (правила сверки сальдо).
3. **Проведение в 1С** — авто или вручную бухгалтером (статусы `sent` vs `posted`).
4. **Отмены/сторно** — как обрабатывать отмену операции nurCRM (сторно в 1С).
5. **Авто-договор из файла** — сейчас ошибки молча игнорируются (`try/except`);
   требуется решение по диагностике/уведомлениям.
6. **Опечатка во флаге** `can_view_building_employess` (двойная `s`) — учитывать
   фактическое имя при доработках.
