# Контракт обмена nurCRM ↔ 1С (денежный контур Building)

> Документ для программиста 1С. Описывает HTTP-сервисы, которые должна опубликовать
> сторона 1С, форматы запросов/ответов и правила надёжности. Реализация на стороне
> nurCRM (модуль `apps/onec`) уже написана под этот контракт.
>
> **Статус полей:** ✅ — зафиксировано кодом nurCRM (менять нельзя без правки кода);
> ⬜ — требует согласования со стороной 1С (заполнить при согласовании).

---

## 0. Как пользоваться этим документом

1. Пройти разделы 1–4 и **вместе с 1С заполнить все ⬜** (URL, маппинг документов,
   ключи контрагентов, валюта).
2. Поднять **sandbox-контур 1С** (раздел 8) и прогнать раздел 9 (сценарии приёмки).
3. После согласования эндпоинтов — прописать их в настройках интеграции
   (`OneCIntegration`: `base_url`, `login`, `password`, `currency`) через
   `PATCH /api/onec/settings/` или в админке.

## 0.1. Фактическая сторона 1С (по выгрузке конфигурации в `onec/`)

Разобрана выгрузка конфигурации. Итог — **это типовая конфигурация, а не кастомная**:

| Что | Значение |
|-----|----------|
| Конфигурация | **«Бухгалтерия для Кыргызстана»**, Фирма «1С», вер. **3.5.1.23** |
| Опубликованные HTTP-сервисы | `exchange_dsl_1_0_0_1` (обмен EnterpriseData), `billing` (биллинг 1С:Fresh), `dt` (файловое хранилище) |
| Web-сервисы | стандартные `EnterpriseDataExchange`, `Exchange_*` (SOAP-обмен) |
| Кастомного REST по документам (`/documents/...`) | **НЕТ** |

**Вывод:** эндпоинтов вида `POST /documents/cashflow` на стороне 1С сейчас **не существует**.
Реальные варианты интеграции — раздел 0.2. Имена документов теперь известны точно
(типовые, раздел 3.3), маппинг больше не «на предположениях».

## 0.2. Развилка по транспорту

> **РЕШЕНИЕ: Путь B — кастомный HTTP-сервис на 1С.** 1С-программист публикует
> HTTP-сервис (по образцу `billing`), принимающий JSON из разделов 3.x и создающий
> типовые документы (раздел 3.3). Клиент `apps/onec` уже готов и переделки не требует.
> Этот документ — ТЗ для 1С-стороны.

| | **Путь A — EnterpriseData (родной обмен)** | **Путь B — кастомный HTTP-сервис** |
|---|---|---|
| Суть | Формируем сообщения в универсальном формате EnterpriseData и грузим через `exchange_dsl` / SOAP-обмен; типовая сама создаёт документы | 1С-программист публикует HTTP-сервис (как `billing`), принимающий наш JSON и создающий ПКО/РКО/Реализацию |
| Разработка на 1С | Почти не нужна (механизм типовой), но нужны правила конвертации (КД 2.0) и узел обмена | Нужна — написать сервис и обработчики |
| Наш клиент | Переписать `apps/onec`: генератор EnterpriseData XML + протокол узлов обмена (тяжело) | **Уже готов** — `apps/onec` шлёт JSON как есть |
| Плюсы | Поддерживается вендором, переживает обновления типовой | Простой контракт, быстрый старт, полный контроль формата |
| Минусы | Сложный формат, batch-файлы, асинхронность | Кастомный код на 1С надо поддерживать при обновлениях |

> `billing`-сервис (`СчётНаОплатуПокупателю`) — это механизм биллинга **1С:Fresh**
> (эндпоинты `/setup`, `/uninstall`, `/setup_result` — типовой API сервис-провайдера),
> он для тарификации подписчиков облака, **не** для проводки денег Building. Не подходит.

## 2. Ключевые правила (обязательны к реализации на стороне 1С)

### 2.1. Идемпотентность по `external_id` — КРИТИЧНО
Каждый документ несёт `external_id` — **UUID операции из nurCRM**. При повторном
запросе с тем же `external_id` 1С **обязана вернуть уже созданный документ, а не
создавать дубль**. Мы шлём «at-least-once»: при таймаутах/сбоях запрос повторяется.
Без дедупликации по `external_id` в 1С появятся дубли ПКО/РКО/реализаций.

Рекомендация для 1С: хранить `external_id` в реквизите документа (или в отдельном
регистре сведений «Соответствие nurCRM ↔ 1С») и искать по нему перед созданием.

### 2.2. Семантика ответов (влияет на ретраи nurCRM)
nurCRM трактует HTTP-код так:

| Код от 1С | Трактовка nurCRM | Поведение |
|-----------|------------------|-----------|
| `200/201` | Успех | Сохраняем `onec_id`/`number`, статус `sent`/`posted` |
| `401` | Протух токен | Сбрасываем токен, **один повтор** |
| `408`, `429`, `5xx` | Временная ошибка | **Ретрай** с экспоненциальным backoff (30с→1ч) |
| прочие `4xx` (400/403/404/409/422) | Бизнес-ошибка данных | **Без ретраев**, статус `failed`, разбор вручную |

> Поэтому: ошибку валидации данных 1С должна отдавать как `4xx` с телом-описанием,
> а не как `500`. Иначе nurCRM будет бесполезно ретраить заведомо битый документ.

### 2.3. Тело ответа (единый формат для всех документов) ✅
```json
{
  "onec_id":  "<GUID документа в 1С>",   // читается nurCRM → onec_external_id
  "number":   "ПКО-000123",              // читается nurCRM → onec_number
  "posted":   true                        // true = документ проведён; false = только создан
}
```
- `posted: true` → статус записи в nurCRM = `posted`; `false` → `sent`.
- При бизнес-ошибке (`4xx`) тело: `{ "error": "текст для оператора" }`.

## 3. Outbound: документы nurCRM → 1С

### 3.1. Общий конверт запроса ✅
Все документы приходят одним конвертом, различаются `source_type` и эндпоинтом:
```json
{
  "external_id": "UUID операции nurCRM",
  "source_type": "cashflow",
  "operation":   "create",            // create | update | cancel(сторно)
  "occurred_at": "2026-07-23T10:00:00+06:00",
  "company":     { "id": "UUID", "name": "ООО ..." },
  "amount":      "150000.00",         // строка, 2 знака
  "currency":    "KGS",               // KGS | USD (см. п.6)
  "...":         "поля, специфичные для документа"
}
```

### 3.2. Реализованный документ — **Касса (cashflow)** ✅
- **Эндпоинт (предлагаемый):** `POST {base_url}/documents/cashflow` ⬜ подтвердить путь
- **Маппинг:** `doc_kind = "pko"` → **Приходный кассовый ордер**;
  `doc_kind = "rko"` → **Расходный кассовый ордер**.
- **Тело (реальный payload из nurCRM):**
```json
{
  "external_id": "9f1c...-uuid",
  "source_type": "cashflow",
  "operation": "create",
  "doc_kind": "pko",
  "occurred_at": "2026-07-23T10:00:00+06:00",
  "company": { "id": "uuid", "name": "ООО Стройка" },
  "cashbox": { "id": "uuid", "name": "Касса №1" },
  "branch_id": "uuid | null",
  "type": "income",
  "name": "Оплата по договору №12",
  "amount": "150000.00",
  "currency": "KGS",
  "meta": {
    "source_business_operation_id": "…",
    "cashier_id": "uuid | null"
  }
}
```

### 3.3. Остальные денежные документы (маппинг заполнить с 1С)

Имена документов — **точные, из типовой Бухгалтерии КР 3.5.1.23** (раздел 0.1):

| # | `source_type` | Операция nurCRM | Документ 1С (точное имя) |
|---|---------------|-----------------|--------------------------|
| 1 | `cashflow` (income) | Приход по кассе | `ПриходныйКассовыйОрдер` |
| 1 | `cashflow` (expense) | Расход по кассе | `РасходныйКассовыйОрдер` |
| 2 | `treaty` | Подписание договора (продажа) | `РеализацияТоваровУслуг` (+ `СчетНаОплатуПокупателю`) |
| 3 | `installment_payment` | Платёж по рассрочке | `ПриходныйКассовыйОрдер` |
| 4 | `procurement` | Закупка | `ПоступлениеТоваровУслуг` (+ `СчетНаОплатуПоставщика`) |
| 5 | `procurement_payment` | Оплата поставщику | `РасходныйКассовыйОрдер` / `ПлатежноеПоручениеИсходящее` |
| 6 | `payroll_payment` | Выплата ЗП | `ВедомостьЗаработнойПлаты` (+ РКО) |
| 7 | `advance` | Аванс | `РасходныйКассовыйОрдер` / `АвансовыйОтчет` |
| 8 | `debt` | Запись/корректировка долга | `КорректировкаДолга` |
| 9 | `barter` | Бартер / взаимозачёт | `КорректировкаДолга` |
| 10 | `barter_cancel` | Отмена бартера | сторно `КорректировкаДолга` |

> Безналичные платежи (карта/банк) при необходимости: `ОплатаПлатежнойКартой`,
> `ПлатежноеПоручениеВходящее/Исходящее`, `ПлатежныйОрдерСписаниеДС`.
> Эндпоинт/способ доставки для каждой строки зависит от выбора Пути A или B (раздел 0.2).

## 5. Inbound: подтверждение проведения (1С → nurCRM)

Опционально, но желательно. Когда бухгалтер проводит документ в 1С — 1С уведомляет
nurCRM, и запись переходит в статус `posted`.

- **Эндпоинт nurCRM:** `POST https://<nurcrm-host>/api/onec/callbacks/posting/` ✅ реализовано
- **Подпись:** заголовок `X-OneC-Signature: sha256=<hex>` — HMAC-SHA256 тела запроса
  на общем секрете (`inbound_secret` из настроек). Запрос без валидной подписи → `401`. ✅
- **Ответы nurCRM:** `200` — приняли (`{status, record_id, new_status}`);
  `401` — плохая подпись; `404` — неизвестный `external_id`; `400` — битый JSON.
- **Эффект:** запись синхронизации → `posted`; для договоров `BuildingTreaty.erp_*`
  → `synced` (write-back через сигнал `document_posted`).
- **Тело:**
```json
{
  "external_id": "UUID операции nurCRM",
  "onec_id": "<GUID>",
  "number": "ПКО-000123",
  "posted": true,
  "posted_at": "2026-07-23T12:30:00+06:00"
}
```

> Альтернатива callback'у — **polling со стороны nurCRM** (Celery beat дёргает
> `GET {base_url}/documents/status?external_id=…`). Выбрать один вариант. ⬜

## 6. Валюта

- В Building операции ведутся в **KGS** и **USD**.
- Валюта документа 1С берётся из настроек компании (`OneCIntegration.currency`,
  значения `KGS`/`USD`) и передаётся в поле `currency`. ✅
- **Согласовать:** формирует ли 1С документы в переданной валюте напрямую, или
  конвертирует в валюту регламентированного учёта (и по какому курсу)? ⬜

## 8. Sandbox / тестовый контур

Нужен отдельный тестовый `base_url` 1С с теми же сервисами, где можно безопасно
слать документы. На нём прогоняются сценарии раздела 9 до включения на проде
(`OneCIntegration.is_enabled = true` для боевой компании).

---

## 9. Сценарии приёмки (acceptance)

| # | Сценарий | Ожидание |
|---|----------|----------|
| 1 | Проводим приход по кассе в nurCRM | В 1С создан **ПКО** на ту же сумму/валюту; в nurCRM запись `sent`/`posted` с `number` |
| 2 | Проводим расход по кассе | В 1С создан **РКО** |
| 3 | Повторная отправка того же `external_id` (эмуляция ретрая) | В 1С **тот же** документ, дубля нет |
| 4 | 1С недоступна (или 500) | Операция в nurCRM прошла; запись `pending`→ретраи→`sent` после подъёма 1С |
| 5 | Кривые данные (нет контрагента) | 1С отдаёт `4xx` + тело; запись `failed`, без бесконечных ретраев |
| 6 | Бухгалтер провёл документ в 1С | (при inbound) callback → запись `posted` |

## 10. Мониторинг на стороне nurCRM (для справки 1С-команде)

- `GET /api/onec/sync-records/?status=failed` — журнал сбоев обмена.
- `POST /api/onec/sync-records/<id>/retry/` — ручной повтор.
- Админка Django: раздел «Журнал синхронизации с 1С» + action «Повторить выгрузку».
