## Блок 1. Возврат чека (POS) → компенсирующее движение

### 1.1. Поведение (R3, R4, R7, R8, R11)

- **R3 — `affects_shift_drawer` компенсирующего `expense`:**
  - **Да.** Для наличной части чека `affects_shift_drawer = True` (при наличии открытой смены). Для безналичных методов (`card`, `mbank`, `optima` и др.) `affects_shift_drawer = False`.
  - Для смешанной оплаты (`split`): в `pos_views.py` возврат разбивается по каждому платежу `SalePayment` пропорционально сумме возврата. Для наличной части создаётся движение с `affects_shift_drawer = True`, для безналичных частей — с `affects_shift_drawer = False`.

- **R4 — Статус компенсирующего `expense`:**
  - На тарифе **«Старт»** статус сразу `approved`.
  - На тарифах с модерацией статус создаётся как `pending` (зеркально исходному чеку продажи).
  - При `reject` исходной продажи в Pending: каскадный реджект компенсирующего возврата запрещён (вызывает HTTP 409 Conflict, тест `test_reject_pos_sale_return_raises_conflict`).

- **R7 — Привязка смены:**
  - **Да по всем 3 ситуациям:**
    1. Исходная смена чека открыта → возврат падает в неё (`shift = sale.shift`).
    2. Исходная смена чека закрыта → возврат падает в текущую открытую смену кассира (без пересчёта и мутации закрытой смены).
    3. Нет открытой смены вообще → `shift = null`, `affects_shift_drawer = False`, возврат разрешён и не блокируется.

- **R8 — `is_defect = true`:**
  - **Да.** Деньги клиенту возвращаются, компенсирующий `expense` на кассу создаётся. Товар на склад при дефекте **не** возвращается (шаг возврата на склад пропускается).

- **R11 — Атомарный откат при ошибке INSERT:**
  - **Да.** Операция возврата выполняется в единой транзакции `@transaction.atomic`. Ошибка создания записи движения полностью откатывает возврат (склад, чек, долг не меняются). Тест: `test_sale_return_atomic_rollback`.

### 1.2. `idempotency_key` (R2)

- **Уникальность:** На модели `SaleReturn` задан `UniqueConstraint(fields=["company", "idempotency_key"])`.
- **Повторный запрос:** При повторном вызове `POST /main/pos/sales/{id}/return/` с тем же `idempotency_key` возвращается **HTTP 200** с сохранённым телом ответа (`response_data`), без дублирования расхода и без повторного возврата остатков.
- **Разные ключи:** Обрабатываются как независимые частичные возвраты, остатки и суммы корректно уменьшаются накопительно.

### 1.3. Частичный возврат и статус чека (R5)

- **Статус чека:** При частичном возврате статус на проводе равен `"partially_returned"`. При полном возврате — `"canceled"`.
- **Сверка смены:** В `CashShift` чеки со статусом `"partially_returned"` учитываются по их текущему `total` (пересчитанному за вычетом возвращённого), а выданная наличность учитывается в расходной части `expense` (`source_kind = "pos_sale_return"` с `affects_shift_drawer = True`), благодаря чему `drawer_expected_cash` и `cash_diff` сходятся точно.
- **Позиции:** По позициям уменьшается `quantity`. Полная история возвращённых количеств сохраняется в `SaleReturn.items_payload`.

### 1.4. Realtime (R9)

- События отправляются в WebSocket-группу компании `notif_company_{company_id}`:
  1. `market.cashflow.created` с полями:
     - `cashflow_id`
     - `cashbox_id`
     - `type: "expense"`
     - `amount`
     - `source_kind: "pos_sale_return"`
     - `source_id`
  2. `market.shift.updated` (если затронута открытая смена):
     - `shift_id`
     - `drawer_expected_cash`
     - `cash_sales_total`

### 1.5. Бэкфилл (R10)

- **Выбрано решение (3) + (2):** закрытые исторические периоды не изменяются автоматически во избежание сдвига закрытой бухгалтерии. Для единичных компаний доступна ручная корректировка через `/crm/kassa`. На проде затронуто менее 10 чеков.

## Блок 3. Настройки кассы (код удаления + макс. скидка)

1. **Вариант хранения:**
   - Выбран **Вариант A**: используется существующее поле `Company.cashier_password`. Это обеспечивает полную совместимость между настройками кассы и существующим разделом «Моя компания».

2. **Эндпоинты:**
   - `GET /main/pos/cashier-settings/` — доступен всем аутентифицированным сотрудникам. Для `owner`/`admin` возвращает `delete_item_code`. Для остальных сотрудников поле скрыто, но отдаются `delete_item_code_required: bool`, `max_discount_percent` и `debt_schedule_version`.
   - `PATCH /main/pos/cashier-settings/` — доступен только `owner`/`admin` (иначе `403 Forbidden`). Валидация: 4–8 цифр, скидка 0–100%, версия рассрочки `v1` или `v2`.
   - `POST /main/pos/cashier-settings/verify-delete-code/` — константное сравнение (`secrets.compare_digest`), лимит 10 попыток/мин (`429 Too Many Requests`), при совпадении кода создаёт временное разрешение на 120 сек в кэше. Всегда возвращает `HTTP 200` с `{ "valid": true|false }`.

3. **Закрытие утечки:**
   - В `CompanySerializer` в `GET /users/company/` поле `cashier_password` исключается для всех ролей, кроме `owner`.

4. **Серверная проверка удаления и лимита скидок:**
   - **Способ передачи кода удаления:** Бэкенд поддерживает **оба** удобных фронтенду варианта:
     1. Прямой заголовок **`X-Delete-Code: <code>`** при запросе на удаление позиции (`DELETE /main/pos/carts/{cart_id}/items/{item_id}/`) или корзины целиком (`DELETE /main/pos/sales/{id}/`).
     2. Предварительный вызов `POST /main/pos/cashier-settings/verify-delete-code/` (действует 120 секунд).
     - Если код задан, а подтверждения нет → `HTTP 403 Forbidden`: `{"detail": "Требуется код удаления или время проверки истекло"}`.
   - **Лимит скидки:**
     - При превышении `max_discount_percent` в `PATCH /main/pos/carts/{cart_id}/items/{item_id}/`, `POST /main/pos/sales/start/` и `PATCH .../order-discount/` возвращается `HTTP 400 Bad Request`:
       ```json
       {
         "detail": "Максимальная скидка — 20.00%",
         "max_discount_percent": "20.00"
       }
       ```
       (скидка не обрезается молча, клиент получает точную ошибку).

5. **Аудит:**
   - Попытки ввода кода логируются в логгер `crm.pos.cashier_settings` (ID пользователя, ID компании, флаг `valid`, IP). Сам секретный код в логи и журнал удалений **не пишется**.

6. **`debt_schedule_version`:**
   - **Да, подтверждаем.** При отсутствии значения на бэкенде отдаётся значение по умолчанию `"v1"`.

## Блок 4. Бэкфилл исторических смен

- **Решение: Вариант (c) — не трогать закрытые смены.**
  - Закрытая кассовая смена является юридически зафиксированным финансовым документом, подписанным кассиром при закрытии. Пересчёт закрытых смен задним числом нарушит историческую бухгалтерскую отчётность.
  - Все новые и текущие смены рассчитываются по исправленной формуле с разделением ожидаемой наличности кассы (`drawer_expected_cash`) и безналичных/складских расходов (`ledger_expected_cash`).
  - Текст для клиентов: *«В закрытых сменах до обновления отображался сквозной баланс с учётом всех типов операций. В текущей версии реализовано разделение наличных ящика кассы и безналичных/складских движений»*.
