# Фронтенд: изменения по товарам и сканированию ШК

Бэкенд закрыл серию проблем («товары исчезают», «сканер возвращает не тот товар»).
Часть требует изменений на фронте. Ниже — что именно и как проверить.

---

## TL;DR

1. **Обработать `409` на всех эндпоинтах поиска по штрихкоду** — новый ответ «неоднозначный ШК».
2. **Поиск по цельному ШК теперь точный** — перестать лить сканер в поле поиска.
3. **Починить свои баги**: сброс кэша после создания, гонка `fetchProductsAsync`, очистка `searchTerm` после скана, сужение `productMatchesBarcode`.
4. Порядок в `products/list/` теперь стабильный (`-seq`) — рефетч не «прыгает».

---

## 1. Новый контракт API (обязательно обработать)

### 1.1. `409 Conflict` — неоднозначный штрихкод

Если под отсканированный код (с учётом нормализации и доп-кодов) подходят **разные**
товары, бэкенд больше **не угадывает** (раньше молча брал произвольный). Возвращается:

```json
{
  "ambiguous": true,
  "message": "Штрихкод 4601234 найден у нескольких товаров — выберите нужный вручную.",
  "matches": [
    { "id": "6f0e…", "name": "Вода Легенда 0.5" },
    { "id": "9a2c…", "name": "Вода Легенда 1.0" }
  ]
}
```

**HTTP-статус: `409`.**

Что сделать на фронте:
- Не считать `409` фатальной ошибкой (проверить общий axios/fetch-обработчик — он не должен показывать «ошибка сервера» / выкидывать из кассы).
- Показать кассиру выбор из `matches` (id → name) и добавить выбранный товар как обычную ручную позицию (по `product_id`).

Эндпоинты, которые теперь могут вернуть `409`:
| Назначение | Метод/URL |
|---|---|
| Обычная касса, скан в корзину | `POST /api/main/pos/sales/{cartId}/scan/` |
| Агентская продажа, скан | `POST /api/main/agents/me/carts/{cartId}/scan/` |
| Склад: поиск по ШК | `GET /api/main/products/warehouse-barcode/{barcode}/` |
| Мобильный сканер (ingest) | внутренний POST по токену |
| Точечный поиск по ШК (find-by-barcode) | внутренний GET |

> **Важно:** в норме `409` почти не появляется — основной штрихкод уникален в компании,
> и обычный скан печатного кода попадает в ветку «точное совпадение». `409` включается
> только там, где раньше в чек уходил **произвольный неверный** товар. Это строго лучше
> прежнего поведения и кассира не блокирует.

### 1.2. Поиск по цельному ШК стал точным

`GET /api/main/products/list/` и `/products/compact-list/`: если `?search=` — это **только
цифры длиной ≥ 8**, бэкенд ищет **точно по `barcode`** (без `icontains` по имени).

Последствие: если сканер случайно попадёт в поле поиска, сетка не подменится
«коинцидентными» именами — вернётся точный товар или пусто. Но лучшее решение — вообще
не пускать сканер в поиск (см. п.2).

### 1.3. Дубликат ШК при создании

Основной и дополнительные ШК уникальны в рамках компании **перекрёстно** (основной код
одного товара не может совпасть с доп-кодом другого). При коллизии:
- ручное создание (`create-manual`) → **400** с сообщением про занятый штрихкод;
- показывать это пользователю, не полагаться только на локальную проверку «поле заполнено».

### 1.4. Стабильный порядок списка

`products/list/` теперь по умолчанию сортируется по монотонному `-seq` (не по `created_at`).
Порядок «сначала новые» детерминирован — при повторном запросе строки не переставляются.
Отдельных действий не требует, но упрощает борьбу с гонкой из п.2.

## 2. Баги на стороне фронта (то, что фронт сам диагностировал)

- **Сброс кэша после создания товара.** `clearProductsCache` существует, но нигде не
  вызывается → возврат на `/crm/sklad` подтягивает старый кэш без нового товара. Вызвать
  после успешного `create-manual`.
- **Гонка `fetchProductsAsync`.** `AddProductPage` при открытии шлёт
  `fetchProductsAsync({ page_size: 100 })`; поздний ответ перезаписывает актуальный список.
  Отменять запрос при уходе со страницы (`AbortController`) или игнорировать ответ по
  устаревшему `requestId`.
- **Очистка `searchTerm` после скана.** Сейчас очистка только по `Enter` в `onKeyDown`.
  Добавить `setSearchTerm("")` в `onComplete` скана и игнорировать поздний ответ по
  `search=<штрихкод>` (тот же requestId-guard).
- **Сузить `productMatchesBarcode`** (productBarcode.js:67): матч **только по точному
  `barcode` / `alternate_barcodes`**, без `article`/`code`/подстроки — иначе после скана
  фокус/штучная продажа открываются не на той позиции.
- **Форма создания** (productUtils.js:323): показывать серверную ошибку `400`/дубль ШК,
  а не только локальную проверку наличия.

## 3. Чек-лист тестирования

- [ ] **Создание → возврат на `/crm/sklad`:** создать товар, вернуться — он остался в
  списке (проверяет сброс кэша + гонку).
- [ ] **Скан «Легенды»:** в чек попадает именно она; поле поиска пустое; сетка не подменилась.
- [ ] **Неоднозначный код:** два товара с кодами, сводящимися к одному (`460123` и
  `0460123`), скан `0000460123` → **409** с двумя `matches`, а не случайный товар.
- [ ] **Дубль основного ШК при создании** → понятная ошибка, товар не создаётся.
- [ ] **Быстрое создание нескольких товаров подряд** → все на месте после обновления списка.

---

## 4. Что запросить у бэкенда для финальной сверки

Снять три реальных ответа по штрихкоду воды «Легенда» и приложить к задаче:
1. `POST /api/main/products/create-manual/` — что сохранилось (`barcode`, `code`, `alternate_barcodes`);
2. `GET /api/main/products/list/?search=<ШК>`;
3. `POST /api/main/pos/sales/{cartId}/scan/` с этим ШК.

Если в ответах `create-manual` / `list` / `scan` расхождений нет, а `scan` отдаёт `409` —
значит на бэке коллизия ШК в данных: бэк запустит `audit_barcode_collisions` и разрулит.
