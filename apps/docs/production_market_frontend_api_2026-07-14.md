## 1. Чек Маркета: изменение цены ≠ скидка

**Правок на фронте не требуется.** Контракт печати прежний: `Итог = Подытог − discount`.

Причина бага была в `Cart.recalc()`: подытог считался от каталожной цены товара, и разница с ценой, введённой кассиром, записывалась в `discount`. Теперь подытог считается по фактической цене продажи, а `discount` = только явные скидки (на строку + на заказ).

Что приходит в `GET /main/sales/json/{sale_id}/receipt/`:

| Сценарий | `price` | `line_discount` | `discount` | Итог |
|---|---|---|---|---|
| Цена изменена 250 → 230 | 230 | 0 | **0** | 230 |
| Скидка на строку 10 | 250 | 10 | 10 | 240 |
| Скидка на строку 10 + на заказ 10 | 250 | 10 | 20 | 230 |
| Цена 230 + скидка строки 10 | 230 | 10 | 10 | 220 |

Инвариант `Σ(line_total + line_discount) − discount + tax = Σ payments.amount` теперь выполняется для каждого чека.

Заодно исправлена фискализация eKassa: там цена позиции уходила уже нетто (со скидкой внутри), а `discount` слался полный — строчная скидка вычиталась дважды. Теперь фискально отдаётся только скидка на заказ.

**Что проверить:** чек с изменённой ценой — печать и `ReceiptPreviewModal`; итог должен совпадать с принятой суммой.

## 2. Фильтр весовых товаров

```
GET /main/products/list/?is_weight=true    → только весовые
GET /main/products/list/?is_weight=false   → только штучные
GET /main/products/list/                   → все
```

Принимает `true/1/yes/on` и `false/0/no/off` (регистр не важен).

Пустая строка (`?is_weight=`) и нераспознанное значение фильтр **не применяют** — незаполненное поле формы можно слать спокойно, 400 не будет. Комбинируется с остальными параметрами:

```
GET /main/products/list/?is_weight=true&category=<uuid>&preset=out_of_stock
```

## 3. Аналитика производства: прочие расходы и чистая прибыль

### 3.1. Новые поля в `summary`

`GET /main/owners/analytics/` → в блоке `summary` три новых поля. Decimal-строки, присутствуют всегда (нет расходов → `"0.00"`), поэтому карточки на фронте стабильны.

```json
{
  "summary": {
    "revenue": "250000.00",
    "cost_of_goods_sold": "150000.00",
    "gross_profit": "100000.00",
    "gross_margin_percent": "40.00",

    "other_expenses_total": "35000.00",
    "net_profit": "65000.00",
    "net_margin_percent": "26.00"
  }
}
```

- `other_expenses_total` — все approved-расходы кассы за период с теми же фильтрами периода/филиала, что и остальная сводка (аренда, ЗП, транспорт, хознужды).
- `net_profit = gross_profit − other_expenses_total`.
- `net_margin_percent` — при `revenue > 0`, иначе `"0.00"` (деления на ноль нет).

Закупки из прочих расходов **не исключаются** — и это корректно: в производстве закупки через кассу бэкендом не проводятся (`SupplierReceipt` / `Acceptance` не создают `CashFlow`), так что в COGS и в кассовые расходы одна и та же сумма попасть не может.

Существующие `gross_profit` / `gross_margin_percent` не изменились.

### 3.2. Деталка по карточке (модалка)

```
GET /main/analytics/cards/details/?card=other_expenses&date_from=…&date_to=…&limit=50&offset=0
```

Алиас: `card=other_expenses_total`. **Доступ только владельцу/админу** — обычный сотрудник получает 403.

```json
{
  "card": "other_expenses",
  "branch_id": "uuid|null",
  "period": {"type": "month", "date_from": "2026-07-01", "date_to": "2026-07-31"},
  "count": 12,
  "offset": 0,
  "limit": 50,
  "totals": {"other_expenses_total": "35000.00"},
  "items": [
    {
      "id": "uuid",
      "created_at": "2026-07-10T11:20:00+06:00",
      "name": "Аренда",
      "amount": "15000.00",
      "category": {"id": "uuid", "title": "Хознужды"},
      "cashbox": {"id": "uuid", "name": "Касса 1"},
      "cashier": {"id": "uuid", "name": "Айбек У."}
    }
  ]
}
```

Фильтр в деталке идентичен фильтру в сводке, поэтому `totals.other_expenses_total` гарантированно сходится с карточкой.

## 4. Отчёт «Произведено за период»

```
GET /main/production/report/?date_from=2026-07-01&date_to=2026-07-14&shift=day&search=хлеб&limit=25&offset=0
```

Все параметры опциональны. Пагинация limit/offset, сортировка — новые сверху.

```json
{
  "count": 132,
  "next": "…",
  "previous": null,
  "summary": {
    "total_quantity": "1540.000",
    "day_quantity": "980.000",
    "night_quantity": "560.000",
    "total_cost": "125400.50"
  },
  "results": [
    {
      "id": "uuid",
      "product": "uuid",
      "product_name": "Хлеб формовой",
      "quantity": "120.000",
      "unit": "шт.",
      "cost_total": "3600.00",
      "produced_by": "uuid",
      "produced_by_name": "Айбек У.",
      "produced_at": "2026-07-13T21:15:00",
      "shift": "night"
    }
  ]
}
```

Правила:

- `summary` — по всему периоду с учётом `shift` и `search`, **не по странице**.
- `shift` проставляет сервер по местному времени (`Asia/Bishkek`): `08:00:00–19:59:59` — `day`, остальное — `night`. Проверено на границах: 07:30 → `night`, 08:00 → `day`, 19:59 → `day`, 20:00 → `night`.
- `produced_at` — ISO местного времени без смещения.
- `shift=abc` → 400; некорректные даты → 400; период без производств → 200, `results: []`, нули в `summary`.
- Себестоимость (`cost_total`) — стоимость фактически списанного сырья по рецепту.
- Закупка готового товара (без рецепта) производством **не считается** и в отчёт не попадает.

### ⚠️ Важно

**История задним числом не восстанавливается.** Раньше факт производства нигде не сохранялся, поэтому записи появляются только с момента деплоя. У существующих компаний вкладка сначала пустая — это HTTP 200 с пустым списком, не 404.

**Проверить первым делом:** после первого изготовления ГП с рецептом запись должна появиться в отчёте. Условие записи — непустой `recipe` **или** `item_make` в `POST /main/products/create-manual/`. Если `FinishedGoodsAddModal` передаёт рецепт как-то иначе — пришлите тело запроса, поправим условие.

## 5. Зарплата в производстве — новая страница `/crm/production/salary`

Базовый префикс: `/main/production/salary/`. Пагинация `PageNumberPagination` (`?page=&page_size=`, максимум 200). Суммы — Decimal-строки.

| Метод и путь | Кто | Что |
|---|---|---|
| `GET /rates/` | владелец | `[{employee, employee_name, hourly_rate, updated_at}]` |
| `PUT /rates/{employee_id}/` | владелец | body `{hourly_rate}` |
| `GET /piece-rates/` | владелец | `[{product, product_name, amount_per_unit, updated_at}]` |
| `PUT /piece-rates/{product_id}/` | владелец | body `{amount_per_unit}` |
| `GET /work-sessions/?employee=&date_from=&date_to=` | все (свои) | табель часов |
| `POST /work-sessions/` | владелец | `{employee, date, hours, comment}` — upsert по сотруднику+дате |
| `DELETE /work-sessions/{id}/` | владелец | 409, если начисление оплачено |
| `GET /accruals/?employee=&kind=&status=&date_from=&date_to=` | все (свои) | + `summary: {accrued_total, paid_total}` |
| `GET /summary/?date_from=&date_to=` | все (свои) | сводка по сотрудникам |
| `GET /payouts/?employee=&date_from=&date_to=` | все (свои) | история выплат |
| `POST /payouts/` | владелец | `{employee, amount, cashbox, comment}` |

`kind`: `hourly` | `piece`. `status`: `accrued` | `paid` | `canceled`.

### `GET /summary/`

```json
[{
  "employee": "uuid",
  "employee_name": "Айбек У.",
  "hours_total": "8.00",
  "hourly_amount": "800.00",
  "piece_quantity": "200.000",
  "piece_amount": "1000.00",
  "total": "1800.00",
  "accrued": "1800.00",
  "paid": "0.00"
}]
```

### Поведение, важное для UI

- **Начисления создаются автоматически.** Почасовое — при внесении табеля (`hours × ставка`). Сдельное — в момент производства ГП (`quantity × ставка товара`), сотрудник = тот, кто произвёл. Ставка не задана или равна нулю → начисления просто нет.
- **Ставки фиксируются снимком.** Подняли ставку — прошлые начисления не пересчитываются.
- **Правка табеля** пересчитывает начисление, пока оно не оплачено. Если оплачено — **409** с `detail`, нужно показать пользователю.
- **Удаление табеля** с оплаченным начислением — тоже **409**.
- **Выплата** закрывает начисления FIFO (от старых к новым; частично покрытое начисление разбивается) и создаёт **одну** расходную операцию кассы «Зарплата: <сотрудник>». Эта операция автоматически попадает в `other_expenses_total` из раздела 3 и уменьшает чистую прибыль.
- **Выплата больше начисленного** → **400** с телом `{"detail": "…", "balance": "1800.00"}` — остаток можно показать в форме.
- **Права:** сотрудник видит только свои `work-sessions` / `accruals` / `payouts`; запрос чужих данных через `?employee=` → **403**; изменение ставок доступно только владельцу → **403**.
- Сотрудник, у которого есть часы, но не задана ставка, всё равно попадает в `/summary/` с нулевыми суммами — иначе его часы «исчезли» бы из сводки.

Отмены/удаления производства в API пока нет, поэтому отката сдельных начислений тоже нет. Понадобится — добавим вместе с таким потоком.

## 6. История закупок в карточке поставщика

```
GET /main/suppliers/{supplier_id}/purchases/?date_from=2026-06-01&date_to=2026-07-14&limit=50&offset=0
```

```json
{
  "count": 42,
  "next": null,
  "previous": null,
  "summary": {"total_amount": "182500.00", "total_count": 42},
  "results": [
    {
      "id": "uuid",
      "product_name": "Мука в/с",
      "quantity": "500.000",
      "unit": "кг",
      "amount": "27500.00",
      "payment_type": "cash",
      "purchased_at": "2026-07-10T11:20:00"
    }
  ]
}
```

- `payment_type`: `cash` | `transfer` | `debt` | `prepayment`.
- `amount` — цена × количество (снимок на момент операции; изменение товара историю не меняет).
- `summary` — по всему отфильтрованному периоду, не по странице.
- `purchased_at` — ISO местного времени.
- Не-поставщик или поставщик чужой компании → **404**.
- Пустая история → **200**, `results: []`, нули в `summary`.

### Что пишется в историю

| Поток | Эндпоинт |
|---|---|
| Закупка сырья (новая позиция) | `POST /main/items-make/` |
| Докупка сырья | `POST /main/items-make/{id}/purchase/` — **новый** |
| Закупка готового товара с поставщиком | `POST /main/products/create-manual/` (с `client`, **без** рецепта и сырья) |
| Приход товара от поставщика (Магазин) | `POST /main/suppliers/{id}/receipt/` |

Товар, изготовленный из сырья, в историю закупок **не попадает** — за него уже платили при закупке сырья.

### ⚠️ Две правки, нужные от фронта

**6.1. Докупка сырья — перевести на новый эндпоинт.**

```
POST /main/items-make/{id}/purchase/
{ "quantity": "100.000", "unit_price": "55.00", "payment_type": "debt" }
```

Увеличивает остаток, при переданной цене обновляет её, пишет строку в историю закупок и возвращает обновлённый `ItemMake`. `unit_price` необязателен (по умолчанию текущая цена позиции); можно передать `supplier`, чтобы сменить поставщика.

`AddRawMaterials.jsx` сейчас шлёт `PATCH /main/items-make/{id}/` — нужно перевести на `POST …/purchase/`.

Почему не оставили PATCH: через него идёт и обычное редактирование карточки, включая ручную корректировку остатка. Если ловить закупку как «рост `quantity`», любое исправление остатка вверх попадёт в историю как несуществующая закупка.

**6.2. Начать передавать `payment_type`.**

Поле необязательное, но **пока фронт его не шлёт, в журнал пишется `cash`**, и колонка «Долг / Предоплата» будет врать. Значения: `cash` | `transfer` | `debt` | `prepayment` (регистр не важен; пустая строка и мусор → `cash`, ошибки не будет).

Добавить `payment_type` в те же запросы, где фронт уже решает, создавать расход кассы или нет:

- `POST /main/items-make/` — закупка сырья (`RawMaterialAddModal`)
- `POST /main/items-make/{id}/purchase/` — докупка (`AddRawMaterials`)
- `POST /main/products/create-manual/` — закупка готового товара с поставщиком (`FinishedGoodsAddModal` без рецепта)
- `POST /main/suppliers/{id}/receipt/` — приход магазина

### Бэкфилла нет

Журнал наполняется только новыми закупками — у существующих поставщиков карточка сначала пустая. В `ItemMake` истории не было в принципе. Для Магазина её теоретически можно частично восстановить из `SupplierReceiptItem` (там есть даты, количества и цены, но нет типа оплаты) — если нужно, сделаем management-команду.

## 7. Двойной расход кассы по ГП — причина не в бэкенде

По жалобе «в кассу расходом попадает и сырьё, и произведённая из него ГП» проверены все три предполагаемых места. **Бэкенд не создаёт расход ни в одном из них:**

- `POST /main/products/create-manual/` — единственный побочный эффект помимо создания товара — списание сырья со склада. Ни `CashFlow`, ни `Cashbox` там нет.
- Списание сырья (item_make) — чисто складская операция, меняет только `quantity`.
- Сигналов, вешающих расход на создание товара, нет: `post_save` на `Product` только отправляет вебхук.

Более того, во всём бэкенде `construction.CashFlow` создаётся ровно в двух местах: оплата заказа в кафе (**приход**) и выплата зарплаты из раздела 5. Все расходные операции по закупкам создаёт **фронт** через `POST /construction/cashflows/`.

**Наиболее вероятная причина** — условие `!hasRecipeMaterials` во `FinishedGoodsAddModal.jsx` не срабатывает (например, рецепт уходит в поле `item_make`, а флаг считается по `recipe`, или наоборот), и расход всё же отправляется.

**Что нужно, чтобы добить:** взять один конкретный лишний расход из `GET /construction/cashflows/` и прислать его `name`, `created_at` и `source_business_operation_id`. Названия операций жёстко заданы на фронте («Закупка товара: …», «Приёмка: …»), поэтому по имени однозначно определяется, какой модальник его отправил.
