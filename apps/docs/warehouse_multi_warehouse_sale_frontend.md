# Продажа с нескольких складов — Frontend API

Документ для фронта: как оформить **одну продажу** (`SALE`), в которой товары списываются с **разных складов**.

Связанные материалы:
- общий API склада: [apps/warehouse/FRONTEND_API.md](../apps/warehouse/FRONTEND_API.md)
- документы агента (ограничение одним складом): [warehouse_agents_frontend_api.md](./warehouse_agents_frontend_api.md)

---

## 1. Суть изменения

Раньше все строки продажи должны были относиться к одному складу (`warehouse_from` документа).

Теперь для **продажи владельца** (без `agent`):
- в одном документе `SALE` / `SALE_RETURN` / `COMMERCIAL_OFFER` можно добавить товары с **разных складов**;
- склад списания определяется **по карточке товара** (`product.warehouse`), а не только по `warehouse_from`;
- при проведении создаётся **отдельное движение** (`StockMove`) на каждый склад.

Для документов **агента** правило не менялось: один склад, товары из остатков агента.

---

## 2. Эндпойнты

| Метод | URL | Назначение |
|-------|-----|------------|
| `POST` | `/api/warehouse/documents/sale/` | Создать продажу |
| `PATCH` | `/api/warehouse/documents/{id}/` | Обновить черновик |
| `POST` | `/api/warehouse/documents/{id}/post/` | Провести |
| `POST` | `/api/warehouse/documents/sale-return/` | Возврат продажи (та же логика по складам) |
| `POST` | `/api/warehouse/documents/commercial-offer/` | КП без проведения (расчёт, несколько складов OK) |

Базовый префикс: `/api/warehouse/`  
Авторизация: `Authorization: Bearer <access_token>`

## 3. Создание продажи с нескольких складов

### 3.1 Минимальный запрос

`warehouse_from` **необязателен**. Если не передан — сервер подставит склад **первого товара** в `items[]` (нужен для кассы и фильтров в списках).

```http
POST /api/warehouse/documents/sale/
Content-Type: application/json
```

```json
{
  "counterparty": "22222222-2222-2222-2222-222222222222",
  "payment_kind": "cash",
  "comment": "Продажа со склада А и Б",
  "items": [
    {
      "product": "aaaaaaaa-aaaa-aaaa-aaaa-aaaaaaaaaaaa",
      "qty": "10.000",
      "price": "150.00",
      "discount_percent": "0.00"
    },
    {
      "product": "bbbbbbbb-bbbb-bbbb-bbbb-bbbbbbbbbbbb",
      "qty": "5.000",
      "price": "300.00",
      "discount_percent": "5.00"
    }
  ]
}
```

Где:
- первый `product` привязан к складу «Склад А»;
- второй `product` — к складу «Склад Б».

### 3.2 С явным `warehouse_from`

Можно указать любой склад **той же компании** — он используется для кассы/фильтрации, но **не ограничивает** склады строк:

```json
{
  "warehouse_from": "11111111-1111-1111-1111-111111111111",
  "counterparty": "22222222-2222-2222-2222-222222222222",
  "payment_kind": "cash",
  "items": [
    { "product": "товар-со-склада-1", "qty": "2.000", "price": "100.00" },
    { "product": "товар-со-склада-2", "qty": "1.000", "price": "250.00" }
  ]
}
```

## 4. Формат ответа

### 4.1 Документ

Стандартный `DocumentSerializer`. Ключевые поля:

```json
{
  "id": "uuid",
  "doc_type": "SALE",
  "status": "DRAFT",
  "warehouse_from": "uuid",
  "warehouse_from_name": "Склад А",
  "counterparty": "uuid",
  "counterparty_display_name": "Клиент",
  "payment_kind": "cash",
  "total": "2850.00",
  "items": [ "... см. ниже ..." ],
  "moves": [],
  "expenses": []
}
```

После проведения (`POST .../post/`):
- `status` → `POSTED` (credit) или `CASH_PENDING` (cash);
- в `moves` / `expenses` — **по одному расходу на каждый задействованный склад**.

Пример после проведения:

```json
{
  "status": "POSTED",
  "moves": [
    {
      "warehouse": "uuid-склада-A",
      "warehouse_name": "Склад А",
      "product": "uuid",
      "qty_delta": "-10.000",
      "move_kind": "EXPENSE"
    },
    {
      "warehouse": "uuid-склада-B",
      "warehouse_name": "Склад Б",
      "product": "uuid",
      "qty_delta": "-5.000",
      "move_kind": "EXPENSE"
    }
  ],
  "expenses": [ "... те же EXPENSE-движения ..." ]
}
```

### 4.2 Строка документа (`items[]`)

Новые read-only поля:

| Поле | Тип | Описание |
|------|-----|----------|
| `warehouse` | UUID | Склад, с которого спишется товар (из карточки товара) |
| `warehouse_name` | string | Название склада |

Полный пример строки:

```json
{
  "id": "uuid",
  "product": "aaaaaaaa-aaaa-aaaa-aaaa-aaaaaaaaaaaa",
  "product_name": "Товар 1",
  "product_article": "ART-001",
  "warehouse": "11111111-1111-1111-1111-111111111111",
  "warehouse_name": "Склад А",
  "qty": "10.000",
  "price": "150.00",
  "discount_percent": "0.00",
  "discount_amount": "0.00",
  "effective_discount_percent": "0.00",
  "line_total": "1500.00"
}
```

Поле `warehouse` в теле **создания/обновления не передаётся** — склад берётся из выбранного `product`.

## 5. Правила и ограничения

### 5.1 Где работает multi-warehouse

| Тип документа | Multi-warehouse | Условие |
|---------------|-----------------|---------|
| `SALE` | да | `agent` = null (продажа владельца) |
| `SALE_RETURN` | да | `agent` = null |
| `COMMERCIAL_OFFER` | да | `agent` = null |
| Документы агента | **нет** | один `warehouse_from`, товары из остатков агента |
| `PURCHASE`, `RECEIPT`, `WRITE_OFF`, `TRANSFER`, `INVENTORY` | **нет** | один склад на документ |

### 5.2 Обязательные поля

Для `SALE` / `SALE_RETURN` владельца:
- **обязательно:** `counterparty`, непустой `items[]`;
- **необязательно:** `warehouse_from` (автоподстановка из первой строки).

### 5.3 Валидация товаров

- каждый `product` должен быть привязан к складу (`product.warehouse` не null);
- все товары — **одной компании**;
- если передан `warehouse_from`, компания склада и всех товаров должна совпадать;
- остаток проверяется **на складе каждой строки** отдельно;
- для штучных товаров `qty` — целое число.

### 5.4 Касса и оплата

- один денежный документ на **всю сумму** продажи;
- `warehouse_from` (или склад первой строки) определяет **company/branch** для кассы;
- логика `CASH_PENDING` / `cash/approve` / `cash/reject` не менялась.

## 6. Ошибки (400)

| Ситуация | Пример ответа |
|----------|---------------|
| Товар другой компании | `{"items": ["Все товары должны принадлежать той же компании, что и склад документа."]}` |
| Товар без склада | `{"product": ["Товар должен быть привязан к складу."]}` |
| Недостаточно на конкретном складе | `{"detail": "Недостаточно товара 'ART-001' на складе 'Склад Б'. Доступно: 2.000, требуется: 5.000"}` |
| Нет контрагента | `{"detail": "Document requires counterparty"}` |
| Редактирование проведённого | `{"status": ["Нельзя изменять проведенный/ожидающий кассу документ..."]}` |

## 7. Рекомендации для UI

### 7.1 Экран создания продажи

1. **Не блокируйте** добавление товара с другого склада — показывайте колонку «Склад» (`warehouse_name` из ответа или из карточки товара при выборе).
2. При поиске товара можно искать **по всем складам** компании (`GET /api/warehouse/products/?search=...`).
3. `warehouse_from` в шапке документа — опционально:
   - можно скрыть и не отправлять;
   - или оставить селект «Основной склад» для фильтра/отчётов (не влияет на склады строк).
4. Перед `post` проверяйте остаток **по складу каждой строки** (из `product.quantity` / `StockBalance` или отдельный запрос остатков).

### 7.2 Группировка в интерфейсе

Удобно группировать строки по складу:

```
Склад А
  - Товар 1 × 10
  - Товар 2 × 3
Склад Б
  - Товар 3 × 5
─────────────────
Итого: 2 850.00
```

### 7.3 Обновление черновика

`PATCH /api/warehouse/documents/{id}/` с полным массивом `items[]` — как и раньше, старые строки заменяются целиком.

### 7.4 Сценарий «один склад» (обратная совместимость)

Старый формат полностью работает:

```json
{
  "warehouse_from": "uuid-склада",
  "counterparty": "uuid",
  "items": [
    { "product": "uuid-товара-этого-склада", "qty": "1.000", "price": "100.00" }
  ]
}
```

## 8. Пример полного цикла

```text
1. GET  /api/warehouse/crud/warehouses/          → список складов (опционально)
2. GET  /api/warehouse/products/?search=молоко     → товары с разных складов
3. POST /api/warehouse/documents/sale/           → черновик с items[] из шагов 2
4. POST /api/warehouse/documents/{id}/post/      → проведение
5. GET  /api/warehouse/documents/{id}/           → moves[] с двумя EXPENSE по разным складам
```

При `payment_kind=cash` после шага 4 статус будет `CASH_PENDING`; затем кассир:

```http
POST /api/warehouse/documents/{id}/cash/approve/
{"note": "Оплачено"}
```

## 9. Чек-лист для тестирования

- [ ] Продажа с 2+ товарами с разных складов — проводится, остатки уменьшаются на каждом складе
- [ ] Продажа с одного склада — работает как раньше
- [ ] Без `warehouse_from` — документ создаётся, `warehouse_from` подставлен из первого товара
- [ ] Недостаток на одном из складов — 400 с указанием склада и товара
- [ ] Документ агента — нельзя смешивать склады (старое поведение)
- [ ] `SALE_RETURN` с товарами на разные склады — остатки увеличиваются на соответствующих складах
- [ ] В списке документов фильтр `?warehouse_from=` находит документ по подставленному/указанному складу
