### 1. 🔴 [POS Checkout] Оформление продажи в долг без привязки клиента (`payment_method = "debt"`)

- **Файлы:** [`apps/main/pos_serializers.py:458-526`](file:///home/fondante/descktop/NurCRM/NurCRM/apps/main/pos_serializers.py#L458-L526), [`apps/main/pos_views.py:2535-2591`](file:///home/fondante/descktop/NurCRM/NurCRM/apps/main/pos_views.py#L2535-L2591)
- **Точка зрения Пользователя (Кассира):** Кассир может случайно выбрать способ оплаты «Долг» и нажать «Завершить продажу», не указав клиента. Система проводит чек без ошибок. В результате продажа списана, но не понятно, кто именно должен деньги.
- **Точка зрения Тестировщика (QA):** Граничный случай — отправка запроса `POST /api/main/pos/sales/<cart_id>/checkout/` с `{"payment_method": "debt"}` и `client_id = null`. Сервер возвращает status `201 Created` и создает запись `Sale(status='debt', client=None)`.
- **Точка зрения Программиста:** `CheckoutSerializer.validate()` проверяет сумму и способ оплаты, но при `payment_method == Sale.PaymentMethod.DEBT` отсутствует валидация `if not client_id: raise ValidationError({"client_id": "При продаже в долг выбор клиента обязателен."})`. В результате создаются «висячие» долги без привязки к контрагенту, которые теряются из всех отчётов сверки (`/api/main/clients/with-debts/` и `/api/main/clients/<id>/reconciliation/`).
- **Рекомендация:** Добавить обязательную проверку наличия `client_id` в `CheckoutSerializer.validate()`, если `payment_method == 'debt'` или если хотя бы одна строка оплаты в `payments[]` имеет метод `'debt'`.

### 2. 🔴 [Чекаут агента] Падение сервера с 500 `ValidationError` в `checkout_agent_cart` при отсутствии кассы

- **Файлы:** [`apps/main/services_agent_pos.py:252-263`](file:///home/fondante/descktop/NurCRM/NurCRM/apps/main/services_agent_pos.py#L252-L263), [`apps/main/models.py:2175-2182`](file:///home/fondante/descktop/NurCRM/NurCRM/apps/main/models.py#L2175-L2182)
- **Точка зрения Программиста:** Функция `checkout_agent_cart()` создает объект `Sale(shift=None, ...)`. В Django-модели `Sale.clean()` написано:
  ```python
  if not self.shift_id:
      if not self.cashbox_id:
          raise ValidationError({"cashbox": "Укажите кассу (если смены нет)."})
  ```
  В `Sale.save()` вызывается `self.full_clean()`. Если у компании или филиала агента не настроена касса по умолчанию, `_resolve_cashbox()` возвращает `None`, а вызов `Sale.objects.create()` выбрасывает необработанное необрабатываемое исключение `django.core.exceptions.ValidationError`.
- **Точка зрения Пользователя:** Торговый агент завершает продажу в мобильном приложении и получает ошибку `500 Internal Server Error`.
- **Точка зрения Тестировщика (QA):** Запрос от агента в филиале без созданного `Cashbox` приводит к краху запроса вместо понятного ответа `400 Bad Request` (`{"cashbox_id": "Нет доступной кассы..."}`).
- **Рекомендация:** Обрабатывать отсутствие кассы на уровне API-слоя и оборачивать `ValidationError` Django в DRF `serializers.ValidationError`.

### 3. 🟠 [Инвентаризация] Округление и потеря точности весовых товаров при проведении акта инвентаризации

- **Файлы:** [`apps/main/inventory_views.py:122-128`](file:///home/fondante/descktop/NurCRM/NurCRM/apps/main/inventory_views.py#L122-L128)
- **Точка зрения Тестировщика (QA):** В системе весовые товары хранятся с точностью до 3 знаков (грамм, `Decimal("0.001")`, например `1.458 кг`). При проведении акта инвентаризации через `ProductInventorySessionApplyAPIView` код выполняет:
  ```python
  qf = Decimal(str(line.quantity_fact or 0)).quantize(Decimal("0.01"))
  ```
- **Точка зрения Пользователя:** Заведующий складом взвешивает весовой товар (например, сыр: 12.345 кг) и вносит это число в инвентаризацию. После проведения акта в системе остаток превращается в `12.35 кг`. Происходит регулярная искусственная погрешность и списание/начисление граммов.
- **Точка зрения Программиста:** Несогласованность шкал квантования (`Decimal("0.01")` вместо `Decimal("0.001")`).
- **Рекомендация:** Заменить квантование на `Decimal("0.001")` или использовать утилиту `qty3()` / `Product.quantity` decimal_places.

### 4. 🟠 [Журнал движения склада] Отсутствие записей в `StockMovement` при проведении инвентаризации

- **Файлы:** [`apps/main/inventory_views.py:103-142`](file:///home/fondante/descktop/NurCRM/NurCRM/apps/main/inventory_views.py#L103-L142)
- **Точка зрения Пользователя (Управляющего / Бухгалтера):** При просмотре журнала движений склада (`/api/main/stock-movements/`) невозможно увидеть, как изменялись остатки в ходе проведения инвентаризации. Корректировка остатков происходит «втихую».

- **Точка зрения Программиста:** В `ProductInventorySessionApplyAPIView` отсутствует вызов `record_stock_movement(...)`.

### 5. 🟠 [Сырьё и Производство] Необработанная ошибка 500 عند отмене перемещения из готовой продукции в сырьё

- **Файлы:** [`apps/main/views.py:4915-4923`](file:///home/fondante/descktop/NurCRM/NurCRM/apps/main/views.py#L4915-L4923)
- **Точка зрения Программиста:** В `FinishedToRawTransferCancelAPIView` выполняется строка:
  ```python
  raw_item = ItemMake.objects.select_for_update().get(pk=transfer.raw_item_id)
  ```
  Если номенклатура сырья (`ItemMake`) была удалена или переформирована, `.get()` выбрасывает `ItemMake.DoesNotExist`, вызывая падение 500.
- **Точка зрения Тестировщика (QA):** При вызове отмены перемещения удаленного сырья сервер возвращает неконтролируемую ошибку 500.
- **Рекомендация:** Обернуть вызов в `filter(...).first()` и возвращать корректный HTTP 400/404 ответ: `{"detail": "Запись сырья не найдена."}`.

### 6. 🟡 [Продажи в рассрочку / Сделки] Невозможность приёма оплаты кассиром по сделкам чужих клиентов

- **Файлы:** [`apps/main/views.py:2967-2968`](file:///home/fondante/descktop/NurCRM/NurCRM/apps/main/views.py#L2967-L2968), [`apps/main/views.py:3080-3081`](file:///home/fondante/descktop/NurCRM/NurCRM/apps/main/views.py#L3080-L3081)
- **Точка зрения Пользователя (Кассира):** Клиент приходит на кассу внести очередной взнос по рассрочке. Кассир (не являющийся персональным менеджером `salesperson` этого клиента и не имеющий роли `owner`/`admin`) ищет сделку клиента через `POST /api/main/deals/<id>/pay/` и получает `404 Not Found`.
- **Точка зрения Тестировщика (QA):** Запрос на оплату взноса от пользователя с ролью `cashier` или `employee` для сделки клиента, где `client.salesperson != request.user`, блокируется HTTP 404 ошибкой.
- **Точка зрения Программиста:** Чрезмерно жесткая фильтрация `deal_qs.filter(client__salesperson=request.user)`. Кассиры должны иметь право принимать оплату по любым сделкам компании/филиала.
- **Рекомендация:** Разрешить кассирам/сотрудникам филиала проводит оплату взносов по сделкам (`cashier` role Check).

### 7. 🟡 [Аналитика Маржи] Искажение себестоимости COGS при покупке и продажах комплектов/пачек

- **Файлы:** [`apps/main/services/__init__.py:117`](file:///home/fondante/descktop/NurCRM/NurCRM/apps/main/services/__init__.py#L117), [`apps/main/models.py:2406-2430`](file:///home/fondante/descktop/NurCRM/NurCRM/apps/main/models.py#L2406-L2430)
- **Точка зрения Программиста:** В `checkout_cart()` используется `SaleItem.objects.bulk_create(sale_items)`. В Django метод `bulk_create` не вызывает метод `Model.save()`. Хотя себестоимость `purchase_price_snapshot` вычисляется вручную, в случаях когда у товара `purchase_price` не был зафиксирован (или `None`), в БД записывается `0.00`. При этом метод `line_cogs` считает `purchase_price_snapshot * quantity`. В результате аналитика маркета (`analytics_market.py`) считает валовую прибыль 100% (COGS = 0).
- **Точка зрения Тестировщика (QA):** Продажа товаров без заполненной закупочной цены искажает графики маржинальности и маржинальной прибыли в аналитике.
- **Рекомендация:** Выводить предупреждения в аналитике о товарах с нулевой себестоимостью (частично реализовано флагом `cogs_warning`) и добавить валидацию цен при оприходовании.
