## A. Предупреждение о чужой кассе (`cashbox_warning`)

### Зачем

Реальный инцидент 23.09. Касса — это один физический денежный ящик, но открытых
смен на ней может быть несколько (по одной на кассира), у каждой свой
`opening_cash`. Кассир второго этажа открыл смену на «Основной кассе компании»,
где уже была открыта чужая смена, ввёл свой остаток 5899, а при закрытии указал
фактическое содержимое **чужого** ящика — 6888. Получилось расхождение +989 при
нуле продаж и нуле расходов.

Бэк теперь отдаёт данные, чтобы кассир заметил это **до** закрытия смены.
Открытие смены при этом **не блокируется** — бывают легитимные схемы с общей кассой.

### Где приходит

```http
POST /api/construction/shifts/open/     →  201, поле cashbox_warning в теле
GET  /api/construction/shifts/{id}/     →  200, поле cashbox_warning в теле
```

Ключ присутствует **всегда**. `null` — предупреждать не о чем (касса свободна либо
смена уже закрыта). Различать «поля нет» и «поле пустое» не нужно.

### Payload

```json
"cashbox_warning": {
  "code": "cashbox_has_other_open_shift",
  "message": "На кассе «Основная касса компании» уже открыта смена: Балнура Мыломойка. По её данным в ящике ожидается 6888.00 сом. Проверьте, что вы открыли смену на своей кассе — иначе при закрытии будет расхождение на чужие деньги.",
  "cashbox_id": "95bd3a14-72c2-45dd-9b58-b95dd0120a95",
  "cashbox_name": "Основная касса компании",
  "open_shifts": [
    {
      "shift_id": "...",
      "cashier_id": "db063122-f22b-4b5d-8558-8526cda93944",
      "cashier_display": "Балнура Мыломойка",
      "opened_at": "2026-09-23T10:04:59.306874+06:00",
      "opening_cash": "6738.00",
      "drawer_expected_cash": "6888.00"
    }
  ]
}
```

`message` готов к показу как есть, на русском. Если хотите собрать текст сами —
всё нужное есть в `open_shifts`.

**Важно:** `drawer_expected_cash` — это реальное содержимое ящика (начальный остаток
+ наличные продажи чужой смены), а НЕ её `opening_cash`. Именно эту цифру нужно
показать кассиру: в инциденте она равнялась 6888, и кассир сразу бы понял, что
5899 — не отсюда.

### Что показать

1. После успешного `POST /shifts/open/` с непустым `cashbox_warning` — заметный
   баннер или модалка (не toast: toast исчезнет, а смена останется неправильной
   на весь день). Достаточно текста из `message`.
2. На экране смены `/crm/shifts/{id}` — держать баннер, пока смена открыта.
   `GET /shifts/{id}/` отдаёт то же поле при каждом запросе.
3. Полезно дать кнопку «Закрыть и открыть на другой кассе» — в инциденте кассир
   именно так и поступила вручную через 4 минуты после закрытия.

### Чего это НЕ чинит

Если фронт не передаёт `cashbox` в `POST /shifts/open/`, бэк выбирает кассу сам:
при отсутствии проставленных ролей у касс — **по подстроке «основн» в названии**.
Именно так кассира и посадило на чужой ящик (23.09 и ранее 17.09).
**Рекомендация: всегда передавайте явный `cashbox`.** Это снимает первопричину,
предупреждение останется страховкой.

## B. Фильтр «Кассир» в продажах смены — теперь на сервере

Реализованы Q1, Q2, Q3 и опциональный §4.2 из `shift-sales-cashier-filter-backend.md`,
плюс закрыты ограничения L1–L3.

### B.1 Фильтрация (Q1) + размер страницы (L1)

```http
GET /api/construction/cash/shifts/{shiftId}/sales/?cashier={uuid}&page_size=50
```

- `cashier` — id сотрудника. Фильтрует по **продавцу чека** (`Sale.user` — тот же
  источник, из которого строится `cashier_display`), а не по владельцу смены.
- Можно несколько через запятую: `?cashier=<uuid1>,<uuid2>`.
- Невалидный UUID → `400 {"cashier": "Ожидается UUID сотрудника (можно несколько через запятую)."}`
- Кассир без продаж в смене → `200 {"count": 0, "results": []}` (не 404).
- Комбинируется через AND с `status` / `payment_method` / `q` / `date_from` / `date_to` /
  `min_total` / `max_total` / `ordering`.

**`page_size` теперь поддерживается** (раньше не было вообще — отдавалось
жёстко 100 и без возможности изменить, отсюда L1). Потолок — 500.

### B.2 `cashier_id` в каждой продаже (Q2)

В ответе `GET .../shifts/{id}/sales/` у каждого элемента `results` появилось поле
`cashier_id` — строка с UUID или `null`:

```json
{
  "id": "b7e1...",
  "doc_number": 1234,
  "cashier_id": "db063122-f22b-4b5d-8558-8526cda93944",
  "cashier_display": "Балнура Мыломойка",
  "status": "paid",
  "payment_method": "cash",
  "total": "150.00",
  "created_at": "2026-09-23T10:12:00+06:00"
}
```

Поле `user` осталось на месте для обратной совместимости. **Группируйте и
фильтруйте по `cashier_id`, а не по `cashier_display`** — тёзки с одинаковым
ФИО иначе склеиваются в одного человека (L2).

### B.3 Список кассиров для выпадашки (Q3) — `cashier_breakdown`

Отдельный эндпоинт не нужен и `/users/employees/` использовать не надо: там все
сотрудники компании, а нужны только те, кто реально продавал в этой смене.
В `GET /api/construction/shifts/{id}/` добавлено поле рядом с `payment_breakdown`:

```json
"cashier_breakdown": [
  { "cashier_id": "db063122-...", "cashier_display": "Балнура Мыломойка", "sales_count": 12, "sales_total": "4500.00" },
  { "cashier_id": "a1b2c3d4-...", "cashier_display": "Аман",              "sales_count": 5,  "sales_total": "1200.00" }
]
```

- Отсортировано по убыванию `sales_total`.
- Отменённые и возвратные чеки исключены — как в `payment_breakdown`.
- Пустой массив, если в смене нет продаж.

Это же поле закрывает клиентскую агрегацию: считать итоги по кассирам самим
(как сейчас делает `resolveShiftPaymentBreakdown` для оплат) больше не нужно.

### B.4 Что удалить на фронте

В `src/pages/shifts/ui/ShiftDetail.tsx`:

- `cashierOptions` / `moneyCashierOptions` — строятся из загруженной страницы,
  заменить на `cashier_breakdown` из ответа смены;
- клиентскую фильтрацию `productMovements` / `filteredMoneyMovements` по
  `sale.cashier_display === filters.cashier` — заменить на параметр `cashier` в
  `fetchShiftSalesAsync` (`src/entities/shift/model/shiftThunk.tsx`);
- заодно добавить `page_size` в запрос — иначе при >100 чеках список всё ещё
  будет неполным, даже с серверным фильтром.

## C. Уведомления

### C.1 Что изменилось на бэке

Раньше ни одно бизнес-событие не публиковалось — в колокольчик приходил только
локальный расчёт срока годности. Сейчас реально шлются:

| Событие | Когда | Кому |
|---|---|---|
| `market.sale.created` | чек пробит (обычная и агентская касса) | владельцы/админы + кассиры этой кассы, кроме продавца |
| `market.cashflow.pending` | авто-операция ждёт подтверждения | владельцы/админы |
| `market.cashflow.created` | авто-операция проведена | владельцы/админы |
| `market.shift.opened` / `.closed` | открытие/закрытие смены | владельцы/админы |
| `market.debt.created` / `.paid` | долг создан / погашен | владельцы/админы |
| `market.transfer.received` | передана партия товара | получатель |
| `market.product.status_changed` | решение по возврату/браку | инициатор заявки |
| `tariff.expiring` | cron 09:00, за 7/3/1 день | владелец компании |
| `market.product.expiring` | cron 08:00 | владелец компании |

Подтверждённый приход по чеку (`pos_sale`, статус approved) намеренно **не**
шлёт `market.cashflow.created` — иначе на каждую продажу приходило бы два тоста
об одном и том же. Заявки `pending` шлются всегда: по ним нужно действие.

Ещё не подключены: `market.payment.received`, `market.product.received`,
`market.product.written_off`, `market.supplier.return`, `market.debt.overdue`,
`market.stock.low`.

### C.2 Payload

WS-кадр не изменился по структуре, но в `data` теперь есть и `meta`, и `cta_label`:

```json
{
  "type": "notification",
  "data": {
    "id": "52be1578-a679-47da-85c7-6df76a89bf4b",
    "type": "market.sale.created",
    "category": "system",
    "level": "info",
    "title": "Новая продажа",
    "message": "Касса №2: 998,00 сом",
    "url": "/crm/market/cashier",
    "cta_label": "Открыть кассу",
    "is_read": false,
    "created_at": "2026-09-23T12:15:00+06:00",
    "actor_name": "Бекболсун Бекмырзаев",
    "meta": { "sale_id": "...", "cashbox_id": "...", "amount": "998.00", "source_kind": "pos_sale", "source_id": "..." },
    "data": { "...то же, что meta..." }
  }
}
```

`meta` и `data` — один и тот же объект под двумя ключами (`data` оставлен для
старых экранов). Читайте `meta`.

### C.3 Что сделать фронту

Немного — контракт вы уже поддерживаете:

1. **Добавить `market.transfer.received` в `MARKET_REALTIME_EVENTS`**
   (`src/shared/lib/notifications/realtimeEvents.ts`). Сейчас он отрабатывает по
   общему правилу «префикс `market.`», но в enum его нет.
2. **Проверить обработку `unread_count`.** Кадр `{"type": "unread_count", "count": N}`
   теперь приходит чаще: сразу после `connect`, после каждого нового уведомления,
   после `read/` и `mark-all-read/`. Бейдж стоит брать из него, а не считать самим.
3. **Локальный расчёт срока годности можно выключить.** `market.product.expiring`
   приходит с бэка ежедневно в 08:00 как агрегированный дайджест
   (`buildProductExpiryLocalNotification`, `src/entities/product/lib/productExpiry.ts`).
   Локальный тарифный fallback `buildTariffLocalNotification` тоже можно убрать —
   `tariff.expiring` шлётся cron'ом в 09:00.

### C.4 REST

Без изменений в путях. Дополнительно:

- `GET /api/main/notifications/` — отдаёт `unread_count` (как и раньше).
- `POST /api/main/notifications/{id}/read/` — теперь возвращает `unread_count` в ответе.
- `POST /api/main/notifications/mark-all-read/` — теперь возвращает `unread_count`.
- `POST /api/main/notifications/read-all/` — добавлен как алиас того же обработчика.
- WS принимает `{"action": "unread_count"}` — можно запросить бейдж явно.
